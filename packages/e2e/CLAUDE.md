# packages/e2e

Package-specific guidance. See the repo-root `CLAUDE.md` for universal rules (commands, dependency graph, the _Legend_ of field labels, contributing). Italic cross-references name a section that may live in another package's `CLAUDE.md` — most app subsystems are in `packages/app/CLAUDE.md`.

**Owner.** ⚠️ This package belongs to the **Tester** role (`@claude/tester`), not the Implementor — see _The Claude GitHub roles_ in the repo-root `CLAUDE.md`. An Implementor ships behaviour and ends its PR Handoff with a **Testing notes** section; the Tester turns those notes into specs here and runs them. If you are working as the Implementor, don't add or edit specs; make the change testable instead (`aria-label` on new grid controls) and write the notes.

**Purpose.** Playwright functional-test harness — the browser-driven suite that exercises the real app (via `packages/app`'s dev server), as opposed to lint/typecheck/build which only prove the code compiles.
**Where.** `playwright.config.ts` (baseURL, `webServer`, chromium project), `tests/*.spec.ts` (one spec per screen/flow — the nav specs plus `batch-edit.spec.ts`, the persistence suite), (no `helpers.ts` — every query the suite needs is expressible with a built-in locator).
**Surface.** `npm run test:e2e -w packages/e2e` runs the suite headless; `npx playwright test --ui -w packages/e2e` (or `cd packages/e2e && npx playwright test --ui`) for the interactive runner while writing specs; `npx playwright show-report` (from this directory) opens the last HTML report.
**Invariants.**
- ⚠️ `webServer` runs **the built app, not the dev server**: `npm run serve-e2e -w packages/app` (explicit `cwd: "../.."` since `-w` resolves from the monorepo root) — kb build + `public/kb` symlink, then `VITE_E2E=true vite build`, then `vite preview` on **:4173**. Measured motive (#1191): a cold context loads the dev app in ~3.5s/163 requests vs ~1.8s/45 built, and CI's 6 workers otherwise share CPU with vite's on-demand transforms. It also means the suite verifies the artifact that deploys, **service worker included**.
- ⚠️ **`VITE_E2E=true` is what keeps the migration fixtures alive in a production build.** `storage/migration/pass.ts` gates the fixture stores on `DEV || VITE_E2E`; without the flag all six migration-fixture specs fail against a built app. Deploy builds never set it, so nothing test-shaped ships.
- ⚠️ **Port 4173, deliberately not 5173.** `reuseExistingServer` is on locally, and on 5173 it would silently reuse a running *dev* server — the suite would pass against an app nobody deploys. On 4173 the only thing it can ever reuse is a preview. `webServer.timeout` is 300s because the build happens inside it.
- ⚠️ `VITE_DEV_TOOLS` only matters if you point `E2E_BASE_URL` at a **dev** server: the TanStack devtools overlay injects hidden `status:`/`statusCode:` nodes that break substring locators and can intercept clicks. The built app has no overlay, so the default path is immune; run any manual dev server you test against with `VITE_DEV_TOOLS=false`.
- Every test gets a **fresh browser context** (Playwright's default) — no shared IndexedDB/localStorage/sessionStorage between tests, so no `/?purge=true` dance is needed for isolation the way a manual browser session would need it.
- ⚠️ **A spec you haven't run isn't done.** The Tester job installs chromium as a workflow step precisely so the suite can be run in-place (`npm run test:e2e -w packages/e2e`). A new test that fails is a *finding* — report it rather than weakening the test until it passes, and never `test.skip` or delete an existing test to get green.
- ⚠️ **Persistence tests are shaped `edit → reload → assert`.** `batch-edit.spec.ts` exists because the nav specs prove screens *render*, not that they *save* — two silent write-loss bugs shipped green past lint/tsc/build because a save threw inside a fire-and-forget call and nothing reloaded to notice. A new editable flow wants a test here, not just a nav assertion.
- ⚠️ Grid inputs/selects/icon-buttons have **no visible `<label>`**, so they carry an `aria-label` (`"Northern Brewer weight"`, `"Add hop to 4. Boil"`, `"Phase type to add"`) via the design components' `label` prop. That's a real accessibility requirement first — the specs just benefit. Don't strip them, and label new grid controls the same way rather than reaching for a test id.
- ⚠️ **A recipe/batch's name is echoed into its delete-confirm dialog's heading, and that dialog is always in the DOM** (a list row's delete `Action` mounts its `Modal` unconditionally, just closed until toggled) — so once a list row has a delete affordance, a bare `getByText`/`getByRole("heading", {name})` for that name is ambiguous in strict mode. Scope to the row instead: `page.getByRole("listitem").filter({hasText: name})`, as `recipes.spec.ts`'s delete and search tests do. ⚠️ Since #591 the dialog is **portalled to `document.body`**, so it is no longer a descendant of the row — row-scoped locators are now unambiguous by construction, but the page-level ambiguity above is unchanged, and a spec looking for the dialog in the DOM should look at the body.
- ⚠️ **A modal's geometry is worth asserting, and behaviour tests do not cover it.** `recipes.spec.ts` drove the delete dialog end to end for months while it rendered ~185px wide in the top-left corner — it asserts text and clicks, never a box. `batches.spec.ts` and `recipes.spec.ts` each carry an `expectConfirmDialogCentred` that reads `.boundingBox()` against `viewportSize()` and checks equal margins on both axes plus a loose width floor. ⚠️ Keep the floor loose (`> 400`, not an exact width): the failure being guarded is a shrink-to-fit collapse to ~185px, and a pixel-exact assertion breaks on any wording change instead.
- ⚠️ **The spec's nouns are the selectors.** A behaviour that names *a button named "Complete
  Mash"* is queried as `getByRole("button", {name: "Complete Mash"})` — the spec sentence is the
  contract, the Implementor renders that accessible name, and neither side reads the other's code
  (see _packages/spec/CLAUDE.md_, "The spec's nouns are the selectors"). A test that cannot find
  its element by the spec's own noun has found a finding, not a selector problem.
- Prefer `getByRole`/`getByText` (Playwright's built-in locators) over custom query helpers. There is no `helpers.ts` any more: its one export (`activeTabName`) read the selected tab's text in a **plain, non-retrying** call, so `expect(await activeTabName(page)).toBe(x)` raced the UI and flaked in CI. Assert tab state with `await expect(page.getByRole("tab", {name: x})).toHaveAttribute("aria-selected", "true")` instead — a locator assertion, so Playwright retries it.
- ⚠️ **Tab switches are deliberately deferred, so never assert on them without retry.** `usePanelSwitcher` runs `setActive` inside a `useTransition`, and a panel whose content suspends (most of them — they read IndexedDB) keeps the *previous* panel, and the previous `aria-selected`, mounted until it resolves. A non-retrying read straight after `.click()` is therefore racing a documented delay: it wins on a fast machine and loses on a loaded CI runner. Every assertion that a tab became active must be an auto-retrying `expect(locator)` form.
- ⚠️ `page.clock` doesn't mix with **two consecutive immediate writes** (e.g. pause then resume, both fire-and-forget `mutate`s). Freezing time across both races this app's query invalidate/refetch: the second write's optimistic UI update can silently revert to the pre-write value within ~50ms real time, even though the persisted data is correct — a test-harness artifact, not an app bug (the same double-write is reliable under real timers). `brew-timer.spec.ts`'s frozen-clock test only ever does one write before advancing the clock; a test needing two state transitions in sequence should use real `page.waitForTimeout` waits instead.
**Gotchas.** ⚠️ This package's `test` script (`eslint .`) is what `nx run-many --target=test` runs as part of Verify — that's a **lint-only** check, not the Playwright suite. The actual browser run (`test:e2e`) is deliberately **not** in the nx gate / Verify; it runs in its own `.github/workflows/functional-test.yaml`, independently of Verify. ⚠️ **It is also scoped more narrowly: PRs to `mainline` only, where Verify carries no base filter at all** — so a task PR into a story branch gets lint/typecheck/build but no browser run, and the suite first executes on the story's PR. That asymmetry is deliberate (this is the expensive half); the reasoning is in the root CLAUDE.md's _Deployment_ section. Locally, `nx run-many --target=build` treats this package's `build` as the same `echo` no-op `core` uses — there's nothing to compile.
**Env.** `E2E_BASE_URL` (defaults to `http://localhost:4173`) — point it at a already-running instance (e.g. a deploy preview) to skip the `webServer` auto-start; `CI` — set by GitHub Actions, flips `retries` to 2 and `reuseExistingServer` to `false`, and selects the bundled chromium over the local Chrome; `E2E_CHANNEL` — overrides the browser channel in either environment.

⚠️ **Which browser runs is chosen from the environment, and that is load-bearing.** Locally the project sets `channel: "chrome"` and drives the **installed** Google Chrome; in CI it sets no channel and uses Playwright's own chromium, which `functional-test.yaml` installs. The reason is that **Playwright 1.62 ships no chromium build for macOS 13** — `playwright install` refuses outright (*"does not support chromium on mac13"*) and the browser cache stays empty, so every local run dies on a missing executable. That failure reads as *"cannot verify"* rather than as a test failure, which is how three changes in one session reached CI with no local browser check at all; one of them failed CI on an assertion a local run would have caught in seconds. ⚠️ Do not "simplify" this back to a bare `devices["Desktop Chrome"]`: it was a commented-out line to flip by hand, and both directions of forgetting cost something — an unverified local run, or a committed `channel` that breaks CI where no Chrome exists.
