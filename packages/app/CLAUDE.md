## Routing
**Purpose.** File-based routing (TanStack Router) with a generated route tree.
**Where.** `src/routes/*` — routes `/`, `/batches`, `/batch/$batchId`, `/recipes`, `/recipe/$recipeId`, `/recipe/$recipeId_/edit` (delisted, nothing links to it), `/knowledge`, `/disclaimer`. `routeTree.gen.ts` (generated); `main.tsx` (`defaultErrorComponent` renders thrown suspense-fetch errors).
**Invariants.** ⚠️ Never hand-edit `routeTree.gen.ts` (the router Vite plugin regenerates it). Read path params via `Route.useParams()`.
**Gotchas.** ⚠️ Param filenames contain `$` (`batch.$batchId.tsx`) → the shell expands it, and under the `@claude` permission layer that's rejected as "shell expansion syntax in paths". Quote just the dollar: `git rm packages/app/src/routes/recipe.'$'recipeId.tsx`. Retrying with different outer quoting will not work.
**Example.** Rename a param route → write the new file, then `git rm` the old with the `'$'` escape above.

## Breadcrumbs (the page "title")
**Purpose.** A route-owned breadcrumb trail rendered once at the top of every page — it **is** the page title, so screens don't render a redundant heading.
**Where.** `component/breadcrumbs/` — `context.tsx` (context + `useBreadcrumbs`/`useBreadcrumbTrail` hooks + the `dynamicCrumb` factory), `index.tsx` (the `Breadcrumbs` component **and** `BreadcrumbProvider` — the Provider lives here, not in `context.tsx`, so that file stays Fast-Refresh-clean). Mounted in `routes/__root.tsx`: `<BreadcrumbProvider>` wraps the shell, `<Breadcrumbs/>` sits above `<Outlet/>`.
**Surface.** `useBreadcrumbs(crumbs: Crumb[])` — registers a group while the caller is mounted. A `Crumb` is either static (`{label, to?, params?}`) or dynamic (built via `dynamicCrumb(hook, args, transform, rest?)`). `to`/`params` make a crumb a `<Link>`.
**How it works.** Each route calls `useBreadcrumbs` with its own trail; groups accumulate in a `Map` and `useBreadcrumbTrail` flattens them **reverse of registration** (effects fire child-first, so reversing yields parent→child). A **dynamic** crumb defers its data hook into a `<Suspense>`-wrapped label *inside* `Breadcrumbs` — never in the route, so the route itself can't suspend on a name lookup. Pass the hook **by reference + args** (`dynamicCrumb(useRecipeResource, ["user", id], r => r.name)`), not a `() => useX()` thunk (rules-of-hooks).
**Invariants.**
- ⚠️ Pass a **stable** `crumbs` array — a module `const` for a static trail, `useMemo` keyed on the route params for a dynamic one. It drives an effect; a fresh array each render thrashes.
- ⚠️ The container's `shrink-0` and `overflow-y-hidden` classes are **both load-bearing** (see Gotchas) — don't drop them.
**Gotchas.** ⚠️ `DrawerContent` is a fixed-height (`h-full`) flex column whose children overflow it, so **without `shrink-0`** flexbox squeezes the breadcrumb box *below its content height*, and the squeeze varies with the active panel's height → the tab bar wobbles ~1px on tab switches. **`overflow-y-hidden`** cancels the stray vertical scrollbar daisyui's `.breadcrumbs { overflow-x:auto }` otherwise induces on mobile. `/` (home) and `/disclaimer` are **intentionally exempt** — they register no crumbs (home is the hero landing; disclaimer keeps its own `<h1>`).
**Example.** `recipe.$recipeId_.edit.tsx`: `useMemo<Crumb[]>(() => [{label:"Recipes", to:"/recipes"}, dynamicCrumb(useRecipeResource, ["user", recipeId], r => r.name, {to:"/recipe/$recipeId", params:{recipeId}}), {label:"Edit"}], [recipeId])`.

## State (TanStack Query, suspense-first)
**Purpose.** All reads go through suspense wrapper hooks; nothing refetches on its own.
**Where.** `src/state/*` — `useBatches`/`useBatch`; **local editable recipes** `useRecipes`/`useRecipe`/`saveRecipe` (`recipes.ts`, backed by the `recipes` store); **read-only KB catalog** `useKbRecipes`/`useKbRecipe` + `fetchKbRecipe` (`kbRecipes.ts`) + `useKbGrains/Hops/Yeasts`; `useSession`, `query-params`. `queryClient.ts`. ⚠️ The two recipe families are distinct: `useRecipe` reads a user-owned `Recipe` from IndexedDB, the kb hooks read catalog `KbRecipe`s — don't cross them. Screens that need one catalog recipe by id currently go through `useRecipeResource`/`useBatchRecipe` (`state/disambiguation.ts`, backed by `fetchKbRecipe`) instead of `useKbRecipe` — `useKbRecipe` has no call site today but is kept deliberately for future use, not dead code (same treatment as `utils/func.ts`'s unused exports — see _Editing pattern_).
**How it works.** Wrapper hooks use `useSuspenseQuery`, return non-null data, throw on failure; screens wrap them in `<Suspense>` at the route level. All four kb resources are prefetched at boot (`main.tsx`).
**Invariants.** ⚠️ `queryClient` sets `staleTime: Infinity` — every write must explicitly `queryClient.invalidateQueries(...)` (`saveBatch`, `saveSession`, actions in `src/actions/`).
**Gotchas.** Stale data after a mutation ⇒ a missing invalidation is the first suspect.
**Example.** _None._

## Offline-first kb data flow
**Purpose.** Serve kb data from a local IndexedDB cache, hydrating from HTTP on first miss.
**Where.** `src/storage/kb.ts`, the `useKbX` hooks.
**How it works.**
```
useKbX() → IndexedDB hit? return it
         → miss + offline?  throw (rendered by the router error component)
         → miss + online:   importResource() over HTTP → hydrate IndexedDB → return
```
**Invariants.** _None._
**Gotchas.** ⚠️ The local kb cache has **no versioning** — a changed stored shape yields stale data until purged. `/?purge=true` on any URL wipes batches + session + kb stores and redirects home (`component/db-cleanup`).
**Example.** _None._

## Storage (`src/storage/`)
**Purpose.** localforage wrappers for the app's persisted state.
**Where.** `forage.ts` (`Forage<T>` base; keys are `` `${name}#${id}` ``), `batches` (IndexedDB), `recipes` (IndexedDB, store name `"recipes"` — user-owned recipes, distinct from the `kb` cache's `"recipes"` resource entry), `kb` (IndexedDB, one entry per resource), `session` (sessionStorage — collapse/toggle memory, cleared on tab close), `query` + `queryStorageDriver.ts`, `localforage.ts` (driver registration).
**How it works.** `queryStorageDriver.ts` is a **custom localforage driver backed by the URL query string** — a synchronous `Storage`-shaped shim over `URLSearchParams` + `history.replaceState`, using localforage's serializer (values keep JSON types) and a `name/` key-prefix (ignores foreign params). Registered as `LF_QUERYSTORAGE`.
**Invariants.** ⚠️ Query-driver values must be small (they sit in the address bar) and JSON-serializable.
**Gotchas.** URL-backed state **survives an inline refresh but resets on navigation** (the query string is dropped) — which is exactly why the panel switcher stores the active tab there.
**Example.** _None._

## Model boundary: Kb* vs app models
**Purpose.** Two model families with a deliberate transform boundary — catalog shapes vs. batch-instance shapes.
**Where.** `src/model/` (app models: `Batch`, `Grain`, `Hop`, `Yeast`, `Scalar`…), `src/transform/` (the mappers), scalar formatting in `utils/formatting.ts`.
**How it works.** **Kb models** (`KbGrain`/`KbHop`/`KbYeast`/`KbRecipe`) are richer catalog/reference shapes; they flow through kb hooks, caches, dropdowns, and knowledge screens **untransformed**. The transform to app models happens **only at the moment of use** — picking a catalog item in a BatchPlanning dropdown (`kbHopToHop` etc., fills instance defaults like `weight: "0.0oz"`), or instantiating a **KB** recipe into a batch (`createBatch(kbRecipe, …)` → `kbRecipe*To*` mappers, preserving the recipe's real values).
**Invariants.**
- ⚠️ **Every recipe-family model carries a `__type` discriminator** — `"kbRecipe"`, `"kbRecipeTemplate"` (both stamped into the data by kb's builder) and `"recipe"` (the app's own, set by `defaultRecipe` and `kbRecipeToRecipe`). Disambiguate on it; **don't sniff for a field**. `createRecipe` used `"batchSize" in source` to tell a `KbRecipe` from a `KbRecipeTemplate`, which silently inverts the moment a template gains a `batchSize` — a field is incidental, a tag is declared.
- ⚠️ **Narrow by testing the leaf tag, not the base one.** Because `Recipe extends KbRecipe`, `KbRecipe.__type` must admit `"recipe"` (it's `"kbRecipe" | "recipe"`), so `x.__type === "kbRecipe"` narrows the *true* branch only — the else branch keeps the whole union, since a `KbRecipe` tagged `"recipe"` is never excluded. Testing the single-literal side instead (`=== "kbRecipeTemplate"`) narrows **both** branches cleanly, which is why `createRecipe` is written with the template case first. No discriminator can fix this direction: a `Recipe` *is* structurally a `KbRecipe`, so TS can never subtract `KbRecipe` from a union that also holds `Recipe`.
- ⚠️ Never map Kb → app models at download/cache time. `Scalar` convention: `{value: "9.0lb", unit: "lb"}` — the display string embeds the unit; `unit` is the parsing/fallback hint.
- ⚠️ **The brewable is the plan's single source of truth, and a phase is an *instance*, not a kind.** `BrewablePhase.id` is **required** and minted at creation everywhere (`defaultBrewable`, `kbBrewableToBrewable`, the Phases add-row) — not by `ensureBrewableIds`, which only backfills the still-optional assignment/equipment ids. An assignment points at a phase via **`phaseId`**, never a `phaseType`, which is what lets two `"boil"` phases hold different ingredients. Milestones (planned readings) hang off the phase for the same reason; only their *values* live in `batch.tracker`. Don't reintroduce a second batch-level phase list to shadow this one.
- ⚠️ `useJsonEdit`'s `add(dot, value)` takes **`unknown`**, so a new brewable item missing a required field (a phase without `id`/`milestones`) type-checks fine and then fails at runtime — `liveTrackerKeys` throws, and because saves are fire-and-forget the write is **silently lost**. Type the object at the add site (`const phase: BrewablePhase = …`) so tsc catches it.
**Gotchas.** `model/recipe.ts` is now the live editable app model for user-owned recipes — `Recipe extends Entity`, built on app `Scalar`/models (the editable complement to `KbRecipe`), persisted through `storage/recipes.ts` + `state/recipes.ts`. KB-sourced recipes still flow as `KbRecipe` everywhere via `state/kbRecipes.ts`, untransformed. `model/brewable.ts` defines a third family — `Brewable` (`schedule`+`assignments`), the shared schedule/assignments structure a brew-day pilot is being built on; app-local for now (the core/kb long-term home is an open question). `Recipe.brewable: Brewable`, `Batch.brewable: Brewable`, and `KbRecipe.brewable: KbBrewable` all carry one now — no derivation, all narrowing. `defaultRecipe` seeds a brand-new `Recipe`'s with `defaultBrewable()`; `kbRecipeToRecipe` instead narrows the kb data's own `kbRecipe.brewable` via `transform/kbBrewableToBrewable.ts` (narrows loose kb strings into the app's `PhaseType`/`ResourceType`/discriminated `Assignment`, **mints a uuid per phase**, and resolves each assignment's authored `phaseType` to the id of the first phase of that type — authored kb JSON stays type-based, the app works in phase *instances*). `createBatch` builds `batch.brewable` the same way: a deep clone of the recipe's own brewable for a **user** recipe, `kbBrewableToBrewable(kbRecipe.brewable)` for a **kb** one (see _Derived batch data_). The now-dead runtime derivation (`transform/buildBrewable.ts`, which built a `Brewable` from the legacy arrays) has been deleted. (Its `HOP_PHASE_TO_PHASE_TYPE` constant briefly outlived it for the reverse projection, but #149 removed `Hop.phase` from the app model — phase now lives solely on the assignment (today `assignment.phaseId`) — so that constant and `projectHopPhase` are gone too. `KbRecipe.hops[].phase` stays as optional kb source data the app no longer reads.) **The brewable is the editing source of truth** and, since #196, the *only* place a recipe's ingredients/equipment live — the flat `recipe.{grains,hops,yeasts,additives,equipment}` arrays and their `_projectRecipeBrewable` projection are gone, so `saveRecipe` (`state/recipes.ts`) just persists the edited recipe and `createBatch` reads `recipe.brewable` directly. `screen/recipe-edit/` is a thin wrapper — a name/brewer header plus `BrewableEdit`. `screen/batch-planning/` mirrors it — a plain name header (no brewDate; that's a brew-day fact, not a planning one — it lives on BatchSchedule's **Prep** tab, see _BatchSchedule screen_) plus `BrewableEdit` driving `batch.brewable`, saving only `{brewable}` — `updateBatch` takes a `Partial<Batch>`, merges it onto the freshest stored batch, then re-derives. The legacy per-resource sub-panels (`batch-planning/{grains,hops,yeasts,equipment,equipment-phase,phases}.tsx` + their row/add-row files) have been retired. `screen/brewable-edit/` is the **reusable brewable editor**: it takes an already-loaded `brewable` plus an `onChangeBrewable` save callback (and optional `panelsBefore`/`panelsAfter`) from the caller, and only ever reads/writes that brewable through one brewable-scoped `useJsonEdit<Brewable>` the panels share — dot-paths are **relative to the brewable** (`assignments[...]`, `schedule.phases[...]`). The caller owns loading the resource and persisting edits — `recipe-edit/index.tsx` calls `useRecipe` and saves only `{brewable}` via `patchRecipe` (a `Partial<Recipe>` read-modify-write in `state/recipes.ts`), so the sibling Details panel's other-field edits aren't clobbered — the merge happens at the store against the freshest value, no `recipeRef`. recipe-edit injects its recipe-specific **Details** panel (`screen/recipe-edit-details/`, which `patchRecipe`s its own top-level fields and never writes brewable back — a late debounced save after a tab switch would otherwise overwrite a brewable edit) as `panelsBefore`; BrewableEdit adds three brewable panels of its own. **Ingredients** (`brewable-edit/ingredients/`): assignments grouped by `phaseType` (outer collapsible section, position-numbered `1. Mash` in first-appearance order) then `resourceType` (inner subsection); each phase has its own add-row — one merged "resource" dropdown (grains/hops/yeasts, value-encoded `"<type>:<name>"`) plus an **Additive…** option that reveals a text field (additives are freeform, no catalog). `assignment-row.tsx` carries the real resource-narrowed fields (grain/hop headline weight; hop alpha/boil, yeast attenuation/temp/starter, additive weight-or-boil under the row's expander — `Additive` is `{name, boil?, weight?}`, both optional so old boil-only stored additives stay valid; the row branches on which one the resource actually carries, and a new additive defaults to `weight` on a Conditioning phase, `boil` everywhere else via `defaultAdditive(name, kind)`). **Equipment** (`brewable-edit/equipment/`): grouped by phase **instance** (equipment lives at `schedule.phases[i].equipment`, not a flat list) — one collapsible section per phase (`phaseLabel`, e.g. `1. Mash`) with its equipment plus a per-phase add-row from `data/equipment.ts`. **Phases** (`brewable-edit/phases/`): the phases as entries — add / remove / **reorder** only (up/down via `useJsonEdit`'s `move`; `canRemovePhase` blocks removing the last phase of a required type), no equipment nested here. (The legacy per-resource arrays and their `_project*Brewable` projections were retired in #196 — a recipe's ingredients/equipment live only on the brewable now; the batch keeps a **phases-only** re-derive so BatchSchedule's per-phase equipment checkoff still works. The legacy `mash`/`boil` step arrays were **removed outright** in #194 — they were near-dead, so a new representation will be designed from scratch; a `BrewablePhase` carries equipment, not step content.) A **batch's** brewable items (assignments, phases, phase-equipment) carry a stable per-instance `id?: string` — minted by `actions/ensureBrewableIds.ts` (idempotent: `id ??= newId()`, `utils/id.ts`) in the batch **write path**: at `createBatch` and the top of `updateBatch`. `updateBatch` is what stamps ids onto items just added in Planning (the add-rows create items without one), so any brewable that has been saved has ids; recipe and kb brewables never get one. There is no on-load id backfill — dev assumes a pristine store (see the root CLAUDE.md). The batch completion tracker (`batch.tracker: Record<string, TrackerEntry>`, `model/tracker.ts`) keys off these ids, alongside the existing `slug` (catalog identity, shared across instances — `id` is per-instance): a `Ref` (`{on: "assignment"|"equipment", id}` or `{on: "milestone", phaseId, when, kind}`) stringifies via `key(ref)` to an id-keyed entry holding brew-day overlay state (checkoffs, actuals, gravity readings, yeast pitch). `actions/tracker.ts`'s `putEntry`/`pruneTracker` are the only sanctioned writers — a key like `equipment:<uuid>` has colons that `utils/func.ts`'s dot-path `get`/`setIn` won't cleanly address, so tracker writes go through `useJsonEdit`'s functional `mutate` (whole-draft update) rather than a dot-path `update`. `defaultBatch`/`createBatch` seed `tracker: {}`; BatchSchedule's equipment checkoff (#210), post-phase gravity readings (#211), and schedule-ingredient checkoff/actual + yeast pitch date (#212, which also dropped `Batch.pitchedDate` — see _BatchSchedule_) all live there now, eager-pruned on every save — `updateBatch` calls `actions/tracker.ts`'s `liveTrackerKeys(brewable)` (every current `assignment`/`equipment`/mash-or-boil post-gravity `milestone` key) into `pruneTracker`, so a ref dropped from the brewable (ingredient/equipment/phase removed in Planning) drops from the tracker too, and re-adding one mints a fresh id with no prior entry. This is the current batch shape (`tracker` added; the earlier `hydrometer`/`pitchedDate`/`Phase.equipment`/persisted `completed`/`actual` are all gone). The models carry **no `version` field** — there is no migration framework (removed); a stored batch/recipe from older code is not upgraded on load, so purge (`/?purge=true`) if a shape changes.
**Example.** _None._

## Derived batch data (`src/actions/`)
**Purpose.** Some batch fields are **projections of the ingredients**, not edited directly — flat, tagged views rebuilt by `_updateX(batch)` actions (`Object.assign(batch, …)`).
**Where.** `_updateShopping` → `batch.shopping` is now the **only** persisted derivation (it carries user-owned `cost`/`purchased`, so a rebuild has to re-attach them). Schedule, equipment and gravity are all **live views** computed on the screen instead: `actions/deriveSchedule.ts` (`deriveSchedule(brewable) → ScheduleItem[]`, memoized in `screen/batch-schedule/index.tsx`) replaced the old `_updateSchedule` → `batch.schedule` projection once #212 moved the last user-owned field (checkoff/actual/pitch) onto the tracker — the array was left a pure cache of `brewable` with one reader. `actions/batchProgress.ts` is the same shape for **progress**: `isPhaseComplete(tracker, phaseId)` and `currentPhaseIndex(phases, tracker)` (the first not-yet-complete phase, or `phases.length` when all are done) — pure, id-based so it survives phase reorder, and read live by BatchSchedule's Complete button (see _BatchSchedule screen_). `batchProgress(batch)` is the batch-level roll-up over those two — `{phases, completedCount, totalCount, currentIndex, currentPhase, started, complete}` — and is **the** answer to "where is this batch" for every reader outside BatchSchedule. ⚠️ `Batch.status` and `model/statuses.ts` (the old `Statuses` enum: `PREP`→`COMPLETE`) are **gone** — #353 moved BatchSchedule off the field and this removed it outright, seeds included (`data/defaultBatch.ts`, `createBatch`), with no migration (a batch stored with the old field just carries a dead key). Progress is now derived from the batch's own variable phase list, so a brewable with two boils or an extra conditioning phase buckets correctly instead of being squeezed into seven fixed enum values. Two screens read it: **`routes/batches.tsx`**'s four tabs — *Ready* `!started`, *Complete* `complete`, and *Brewing*/*Fermenting* both `started && !complete` split on `currentPhase.type` (`mash`/`boil` vs `ferment`/`carbonation`/`conditioning`, the same boundary the enum encoded) — and **`screen/batch-list/item.tsx`**'s per-item `Status:` line, which shows `"Ready"`, `phaseLabel(phases, currentIndex)` (`"2. Boil"`) mid-brew, or `"Complete"`, so the label and the tab always agree by construction. ⚠️ `complete` requires `totalCount > 0`: a phase-less brewable is 0-of-0, which would otherwise read as both Ready **and** Complete and list the batch under two tabs. The assignment-narrowing helpers `resourcesOf`/`indexedResourcesOf` live in `actions/brewableResources.ts`. `updateBatch` (edit save path), `createBatch` (instantiation). ⚠️ `batch.phases` is **retired** — the BatchSchedule tabs now derive from `brewable.schedule.phases` (see _BatchSchedule_). `data/defaultBatch.ts` is a **factory**, not a module-level const: a shared object gets spread into every batch by reference (`{...defaultBatch}` is shallow), so an in-place mutation of a nested field would leak across every batch made in that session.
**How it works.** Two conventions make rebuilds safe:
- **Reuse-by-reference** — the shopping rebuild matches new items against the previous list by a stable key (`tag:name`) and preserves its *user-owned* fields (`cost`/`purchased`); when nothing it owns changed it returns the **previous object by reference** so the `isEqual` diff stays cheap. ⚠️ This machinery is only needed by a *persisted* derivation. A live view has nothing to re-attach and no stored copy to diff — `deriveSchedule` is a plain pure function and the screen's `useMemo` is its entire cache story. Don't reintroduce a reuse map for it.
- **Trigger diffing** — `updateBatch` takes a `Partial<Batch>`, merges it onto the freshest stored batch (`{...current, ...patch}`), then re-runs the shopping derivation only when `batch.brewable` actually changed (`isEqual` against the stored batch), since that's where the ingredients live; a `{brewDate}`-only patch (or editing the batch name) leaves brewable identical and rebuilds nothing. The partial-merge is what lets BatchPlanning's header and brewable editor each save just their slice without a ref (see _Model boundary_); a full-batch caller (BatchSchedule/Shopping drafts) still works — every key is present, so the merge is a straight replace. Shopping's `cost`/`purchased` is the only persisted-derived-with-state left to protect from a needless rebuild — the live-derived schedule/equipment/gravity views carry none of their own and aren't rebuilt here at all. `createBatch` builds `batch.brewable` first — a deep clone of the recipe's own brewable for a **user** recipe, `kbBrewableToBrewable(kbRecipe.brewable)` for a **kb** one (narrowed straight from the kb data's own brewable, not derived — see _Model boundary_) — then runs `_updateShopping`. `batch-planning` edits `batch.brewable` directly (via `BrewableEdit` — see _Model boundary_); the other batch views source from the brewable too — `_updateShopping`/`deriveSchedule` read their ingredients from `brewable.assignments` (via `resourcesOf`/`indexedResourcesOf`, the latter now also surfacing each assignment's `id`), `batch-summary` via `organicNames`, `batch-schedule`'s write-through `path`s target `brewable.assignments[i].resource.*`, and `batch-schedule`'s equipment checklist reads `brewable.schedule.phases[].equipment` directly and live, matched to a tab by phase type (see _BatchSchedule_). Ingredients/equipment live only on the brewable now — nothing projects them back onto a batch-owned copy.
**Invariants.** _None._
**Gotchas.** ⚠️ Derived fields are **not migrated** (there is no migration framework — dev assumes a pristine store): a batch stored before a derived field existed throws until re-derived or purged (`/?purge=true`). (The old stale-`path` hazard is **gone**: `schedule` used to be persisted and only re-derived on an ingredient edit, so a batch built by older code kept dead write-through paths — a brew-day boil edit then wrote a removed field and was silently lost. Deriving live means the paths are always regenerated from the current brewable.) The standalone Checklists screen + its `_updateChecklists` derivation were **removed**; equipment checkoff moved onto BatchSchedule phases (and, since #210, onto `batch.tracker` — see _BatchSchedule_), and the batch's second tab is now `Shopping`. (`model/recipe.ts` is now the live user-recipe model — see _Model boundary_.) (The recipe side had an analogous `_projectRecipeBrewable`, deleted in #196 once its output arrays were removed — `saveRecipe` now just persists the recipe.)
**Example.** _None._

## Data compatibility (no migrations)
**Purpose.** There is **no migration framework** — it was removed deliberately. Models carry no `version` field, and nothing normalizes stored data on load.
**How it works.** Dev **assumes a pristine local store**: batches/recipes are read straight from IndexedDB and used as-is. A stored object written by older code is **not** upgraded — if a model shape changes, a stale object throws until re-derived or the store is wiped with `/?purge=true` (`component/db-cleanup` wipes batches + session + kb and redirects home).
**Invariants.** ⚠️ Don't reintroduce "ensure"/backfill shims that repair old stored objects (the former `state/batches.ts` `ensureIds` / `state/recipes.ts` `ensureBrewable`), and don't add a `version` field or a migration step "just in case" — this is a proof-of-concept with no data to preserve. Per-instance brewable ids are still minted, but only in the batch **write path** (`ensureBrewableIds` at `createBatch`/`updateBatch`) — that's instance creation, not stored-data repair (see _Model boundary_).
**Gotchas.** _None._

## BatchSchedule screen: configurable phases
**Purpose.** A schedule screen driven by `phases` (config), `schedule` (derived), and the brewable's own equipment kit (derived live, checked off through the tracker).
**Where.** `screen/batch-schedule/` — `index.tsx` + `item-row.tsx` + `equipment.tsx` + `reading.tsx` + `complete-phase.tsx` (the old per-step screens were deleted). Model commentary in `model/batch.ts`.
**How it works.**
- **One sub-tab per `brewable.schedule.phases[]` entry** (the `compact` _PanelSwitcher_), titled by `phaseLabel` (`"2. Boil"`) and keyed by `phase.id`. ⚠️ `batch.phases` is **gone**: the brewable is the plan's single source of truth, so a second Boil phase is its own tab with its own ingredients, equipment and readings — never merged into the first. Collapse state keys off `phase.id`, not a renamable name. A leading **"Prep"** tab (a static `PanelSwitcherContent`, sibling to the `.map()`-produced phase tabs, not wrapped in a Fragment) holds the brew-day `brewDate` and `packaging` fields — neither is phase-derived, so they carry no number prefix and never route through `phaseLabel`; the default tab stays the first phase (`phaseLabel(…, 0)`), not Prep. `packaging?: "keg"|"bottle"` (`model/batch.ts`) is a batch-only brew-day fact, not part of `Brewable`/`Recipe` — a recipe doesn't know how a given batch will be packaged — edited via a plain `allowNull` `DataGridSelect`/`update("packaging", …)`. The screen's old batch-level **Status** `DataGrid` (a free-form `statuses` dropdown above the tabs) is **gone** — progress is per-phase now, see _Phase completion_ below.
- **The schedule** — a **live view**, not a batch field: `deriveSchedule(data.brewable)` inside the screen's `panels` `useMemo` (deps `[data.phases, data.brewable]`), each item carrying its source assignment's `id`, its **`phaseId`** (the phase instance it belongs to) and a `kind`; a tab shows the items whose `phaseId` matches it, grouped by `kind` under collapsible headers. `batch.schedule` as *storage* is gone — same treatment equipment and gravity already had.
- **Equipment** — no longer a batch-owned copy (#210 retired `Phase.equipment`/`_projectBatchBrewable`). each tab reads its **own** phase's `equipment` directly (`phase.equipment`) — no type-matching or flat-mapping across phases — the same kit BatchPlanning's `BrewableEdit` equipment panel manages, so an add/remove/rename there shows up here immediately, id-stable (`ensureBrewableIds`). `equipment.tsx` reads each item's checked state from `batch.tracker[key({on:"equipment", id})]?.completed` and calls `onToggle(id)`; `index.tsx`'s `toggleTrackerCompleted(ref)` (shared with the ingredient rows' checkoff — `toggleEquipment` is a thin wrapper over it) computes the next tracker via `putEntry` inside `useJsonEdit`'s functional `mutate` (a tracker key isn't dot-path addressable — see _Model boundary_ / _Editing pattern_), saved **immediately** (`mutate(fn, true)`), like the old checkbox's `toggle()` did, just through the tracker instead of a `phases[].equipment[].completed` write.
- **Ingredient checkoff/actual + yeast pitch (#212)** — `item-row.tsx`'s `BatchScheduleItemRow` computes its own ref (`{on:"assignment", id: item.id}`) from the row's `id`. `completed` reads `entry?.completed` (`entry` is `batch.tracker[key(ref)]`, passed down by `index.tsx`) and its checkbox calls `onToggle(ref)` → `toggleTrackerCompleted` (immediate, like equipment). `actual` reads `entry?.actual` and writes via `onPatch(ref, {actual})` → `index.tsx`'s `patchTracker` (debounced `mutate`, mirroring the reading rows below — see _Model boundary_). The yeast row's pitch date is an `extra: ScheduleDetail` with no `path` (tracker-backed instead of dot-path-backed); it reads `entry?.date` and writes via the same `onPatch(ref, {date})`, so each yeast assignment tracks its own pitch date. `deriveSchedule.ts` maps assignments 1:1, taking each row's `id` and `phaseId` straight off its assignment; the old `phase:kind:name` `keyer()` re-attachment key is gone — `id` is already unique and rename/reorder-stable.
- **Readings (milestones)** — `reading.tsx`'s `BatchScheduleReading` is a **kind-aware** component, instantiated once per `MilestoneKind` (today `"gravity"`, `"volume"`, `"temperature"`, `"pressure"`, `"kegDate"`, `"bottleDate"`) at the bottom of each phase's panel in `index.tsx`, each its own `unitOptions`/`headerLabel`/`addLabel`/`defaultLabel` (a module-level const per kind, e.g. `GRAVITY_UNIT_OPTIONS`/`VOLUME_UNIT_OPTIONS`/`TEMPERATURE_UNIT_OPTIONS`/`PRESSURE_UNIT_OPTIONS`). All instances read/write the same `phase.milestones[]` array; each renders only the entries whose `milestone.kind` matches its own `kind` prop (pairing each milestone with its real index in the unfiltered array first, since that index is what the `update`/`remove` dot-paths address), so several kinds can coexist on one tab as independent grids. `onAdd` mints a new `Milestone` with `label: defaultLabel` — `defaultLabel` differs per kind (gravity stays `"Reading"`, volume is `"Volume"`, temperature is `"Temperature"`) precisely so a fresh milestone of each kind on the same tab gets a distinct accessible name. `"pressure"`/`"kegDate"`/`"bottleDate"` are the first kinds **gated to a specific `phase.type`** (`index.tsx` only renders them on the carbonation/conditioning tab) — gravity, volume and temperature stay unconditional on every tab. `"kegDate"`/`"bottleDate"` are also the first **date-only** kinds: `BatchScheduleReading`/`BatchScheduleReadingItem` take an optional `dateOnly` flag that skips the reading/unit inputs entirely and renders the date field (normally behind the row's expander) as the row's own primary control, so that entry's `TrackerEntry` only ever gets a `date`, never a `.reading`.
- **Phase completion (the batch's real progress)** — `complete-phase.tsx`'s `BatchScheduleCompletePhase` renders a **"Complete `<phaseLabel>`"** button (`aria-label` the same string) behind a `Modal`/`useModal` confirm (`This can't be undone.`, mirroring `component/confirm-delete-button`). Confirming calls `index.tsx`'s `completePhase`, which writes `putEntry(tracker, {on:"phase", id: phase.id}, {completed: true})` through `mutate(fn, true)` — **immediate**, like the equipment/ingredient checkoffs. The button renders **only** on the phase whose index equals `currentPhaseIndex(brewable.schedule.phases, tracker)` (`actions/batchProgress.ts`), computed in its own `useMemo` — deliberately *not* folded into the `panels` memo, whose deps must stay `[data.brewable]` so a checkoff doesn't re-derive the whole schedule.**Invariants.**
- ⚠️ Phase **names are the identity** (React key, tab title, query-param value) — renaming one orphans its stored collapse/active-tab state.
- ⚠️ **Completion is forward-only, and gating the button to the current phase is the whole enforcement.** Every phase before `current` is complete by construction (that's what makes `current` the *first* incomplete one) and every phase after it is unreachable until `current` completes, so an out-of-order write is never offered — no extra validation, and deliberately **no uncomplete control anywhere**. Once `current === phases.length` no tab shows a button. The leading **Prep** tab isn't a `brewable.schedule.phases[]` entry, so it never participates and doesn't shift the indexing.
- ⚠️ **The current phase's tab is never disabled**, even with nothing scheduled in it. `PanelSwitcher` disables a tab whose panel has no children, so an empty current phase would otherwise be unclickable and the progression would wedge with no way to advance — `index.tsx` therefore renders the panel when `hasContent || isCurrent`, with the schedule content itself still gated on `hasContent`.
- ⚠️ **The brew-day screen never edits the plan.** Every editable value on a schedule row is **tracker-backed**, and the as-brewed values mirror the plan's own shape: `TrackerEntry.resource` is a `ResourceActuals` (`Partial<Omit<Grain & Hop & Yeast & Additive, "name">>`) keyed by the **same field names** as `assignment.resource` — a hop records `resource.weight`/`resource.boil`, a yeast `resource.temp`. `date` is universal (pitch date, reading date) and `reading` is milestone-only — shared by every `MilestoneKind`, not gravity-specific. `ScheduleItem` carries the *planned* `resource` read-only plus its `resourceType`; the screen's `COLUMNS` const maps a resource type to the fields worth a column, and each column reads plan and actual from the **same key**, so adding e.g. `"alpha"` for hops needs no model, tracker or derivation change. A row shows the plan until an actual is entered, then notes each drift (`(7.4% · plan 1.0oz · plan 60min)`). The old `path` dot-path write-through into `brewable.assignments[i].resource.*` is **gone** — editing the plan is Planning's job; doing it from here overwrote the recipe-derived intent with no record of it. Grains have no secondary value (checklist + amount only).
**Gotchas.** ⚠️ `putEntry` merges `resource` **one level deeper** than the rest of the entry — each column patches its own field, so a plain spread would let recording a boil time silently wipe a weight recorded a moment earlier. `ScheduleItem.resource` is the derived plan; `TrackerEntry.resource`'s fields are set only when what happened differed — capturing brew-day facts *without* rewriting the plan the shopping list aggregates from. `extra: ScheduleDetail[]` are secondary fields (e.g. pitch date) behind the row's expander — a field, not a step; all of them are tracker-backed now, so `ScheduleDetail` has no `path`. `assignment:<id>`/`equipment:<id>`/`milestone:<id>` tracker keys for a brewable item removed in Planning are dropped on the next save (`updateBatch`'s eager-prune — see _Derived batch data_), not immediately on the edit itself.
**Example.** _None._

## Editing pattern (`hooks/useJsonEdit.ts`)
**Purpose.** The workhorse for draft editing — local draft + dot-path updates + debounced saves. Generic over any object (`<T extends object>`): a whole `Entity` (Batch/Recipe) or a sub-object like a `Brewable` (what `BrewableEdit` edits, merging it back onto the recipe on save).
**Where.** `hooks/useJsonEdit.ts`; dot-path `get`/`set`/`setIn` in `utils/func.ts`.
**How it works.** Local draft state; `update("hops[0].boil.value", v)` dot-path writes; **350 ms-debounced** saves; `updateScalar` re-formats on blur using the **previous scalar's unit** as the default when the user types a bare number. Editors read the draft through a ref so their identity stays stable across edits (memoized rows don't re-render). Paths support dot and bracket segments. The returned tuple is `[data, update, updateScalar, toggle, add, remove, move, mutate]` — `move(path, from, to)` is a bounds-checked swap backing the Phases panel's reorder controls; `mutate(fn, immediate?)` is a **functional whole-draft update** (`fn(latestDraft) => nextDraft`) for edits a dot-path can't express — e.g. a map keyed by `"equipment:<uuid>"`, whose colons aren't dot-addressable. Because `mutate` reads the freshest draft through the hook's own ref, a consumer no longer needs its own `useRef` to avoid a stale closure while keeping a stable callback (this is how BatchSchedule's tracker toggles dropped their `dataRef`).
**Invariants.** ⚠️ Uses hand-rolled `utils/func.ts`, **not lodash** — don't add lodash (now lint-enforced). ⚠️ `utils/func.ts` is a deliberate mini-stdlib, so some of its exports have **no call site yet** (`set` — the mutating twin of `setIn` — plus `intersection` and `pipe`). That's intentional surface, **not** dead code: leave them. The resync effect deep-compares before accepting store emissions, so a re-emitted identical batch doesn't disturb an in-progress draft.
**Gotchas.** _None._
**Example.** `update("hops[0].boil.value", v)`.

## PanelSwitcher (`component/panel-switcher/`)
**Purpose.** A fully React-controlled tablist/tabpanel (button tabs, not DaisyUI's radio+CSS pattern) that mounts **only the active panel**.
**Where.** `component/panel-switcher/` (`usePanelSwitcher` drives it). Consumers declare panels as direct children: `<PanelSwitcher name="batch" defaultTab="Planning"><PanelSwitcherContent title="…">…` (the batch tabs are Planning / Shopping / Schedule / Summary).
**How it works.** `PanelSwitcherContent` never renders; `PanelSwitcher` reads its props via `React.Children`. Tab switches run inside a `useTransition`. A `compact` prop gives tighter tabs (`tabs-sm`, in-flow not mobile-full-bleed) for a nested sub-nav — used by BatchSchedule (one sub-tab per phase) and BatchPlanning (`Ingredients`/`Equipment`/`Phases`). Unmount-on-switch is safe because edits persist through debounced saves and UI state persists (collapse → `session`, active tab → `query`).
**Invariants.**
- ⚠️ Panels must be **direct children** — a `.map()` array is fine (`Children.toArray` flattens it), but a **wrapping Fragment is not** (it collapses to one child and the tabs vanish). A panel with no children renders as a disabled tab.
- ⚠️ The tablist sits **outside** the Suspense boundary (tabs stay visible while content loads), and the boundary lives **inside** PanelSwitcher and must stay mounted across switches — per-panel `<Suspense>` wrappers would flash their fallback on every switch.
**Gotchas.** _None._
**Example.** BatchSchedule builds one panel per phase from a `.map()` — the array-child case above.

## Styling (Tailwind v4 + DaisyUI v5, nord theme)
**Purpose.** CSS-first config, no tailwind.config file, no PostCSS. **design owns the shared tokens** — the daisyui `nord` theme declaration, `--font-sans`, and the SRM `--color-beer-1`…`--color-beer-50` scale (rendered by design's `SrmAvatar`) live in `packages/design/src/tokens.css`; app and www each `@import "@brewdocs.beer/design/src/tokens.css";` it by bare specifier rather than declaring their own copies. Remaining app-only tokens (`--breakpoint-xs`, `--text-2xs`, the `--radius-selector` override, `--leading-11/12`, `.dg-collapsed ~ *`) stay in `packages/app/src/styles.css` — only what's byte-identical across consumers has moved so far.
**Where.** `src/styles.css` — the `@import` of design's `tokens.css`, the app-only `@theme` block, the `@source` for design, and unlayered `:root` overrides at the bottom. `packages/www/src/styles/global.css` is the minimal counterpart (just the `tokens.css` import + `@source`).
**Invariants.**
- ⚠️ `@source` and `@import` are unrelated mechanisms and **both are required** — don't conflate them. `@source "../../design/src";` makes Tailwind's *class scanner* look inside design's `.tsx` files for utility classes it should generate; `@import "@brewdocs.beer/design/src/tokens.css";` ships design's *token declarations* (the `@plugin`/`@theme` text) into the consumer's own Tailwind pipeline. Removing either silently drops styling with no build error — verify visually, not just by a green build.
- ⚠️ The bare-specifier import resolves via normal Node resolution (follows the workspace symlink) — this is *different* from Tailwind's directory auto-scan, which doesn't follow symlinks (that's why `@source` must be spelled out explicitly).
- ⚠️ `tokens.css` must never `@import "tailwindcss"` — every consumer (and `design.css` itself) already does, and a double import breaks the build.
- ⚠️ DaisyUI theme variables live in the `base` cascade layer, which beats `@theme` (the `theme` layer) — overriding a daisyui token (e.g. `--radius-selector`) requires a plain **unlayered** `:root {}` rule.
- ⚠️ Some DaisyUI behaviors are compound selectors keyed to **literal class names** (e.g. `.collapse`'s arrow needs the literal `collapse-arrow`) — applying them only via responsive variants (`max-lg:collapse-arrow`) silently breaks them.
- ⚠️ Don't add a `tabIndex` to a `.collapse` element — it force-opens via `:focus-within` in v5.
**Gotchas.** Tailwind utilities override DaisyUI component styles (cascade layers), so `checked:bg-primary` etc. on components is the intended customization mechanism.
**Example.** The unlayered `--radius-selector` override at the bottom of `styles.css`. `packages/www/src/styles/global.css` is the minimal working example of the shared-tokens stack; `packages/app/src/styles.css` is the maximal one (adds its own app-only tokens on top).

## kb serving during dev/build
**Purpose.** Serve kb data from a symlink in dev, and deliberately keep kb **out** of the app's build output.
**Where.** `npm run link-kb` (symlinks `public/kb → ../../kb/dist`), wired to `predev` only.
**How it works.** `link-kb` runs **only via `predev`** (dev). The pre-`build` hook is named `devprebuild`, *not* `prebuild`, on purpose — so `link-kb` does **not** fire before `vite build`, keeping the kb symlink/JSON out of `dist` and the app S3 bucket. kb ships independently to its own bucket (`app-kb-prod`, served at `/kb/*`), so the app must not carry its own copy.
**Invariants.** ⚠️ **Don't "fix" `devprebuild` to `prebuild`** — that reintroduces kb into the app publish.
**Gotchas.** A clean/CI build (no `public/kb`) produces `dist` with **no `dist/kb`** — so in prod the SW does *not* precache kb; offline kb comes entirely from the IndexedDB hydration flow (_Offline-first kb data flow_). But once you've run the dev server, the leftover `public/kb` symlink makes a **local** `npm run build` include + precache `dist/kb/*.json` — so a local `build`/`preview` misrepresents prod offline behavior (`rm public/kb` to reproduce CI).
**Example.** _None._

## Linting
**Purpose.** eslint 9 flat config, the verification gate (`npm test` = `eslint .`). **Ratchet policy: errors block, warnings inform** — `npm test` exits 0 while warnings remain.
**Where.** Shared base: `packages/core/eslint.config.base.js` (dev tooling, **not** `core/src`). Per-package overlays: `packages/app/eslint.config.js`, `packages/www/eslint.config.js`, `packages/design/eslint.config.js`.
**How it works.** The **base** (shared by app + www + design) holds the common rules: `@stylistic` (double quotes, semicolons, 4-space indent); `import-x/order` (external → `@brewdocs.beer/*` → `@/` → relative, alphabetized) + `import-x/no-relative-packages`; `react-hooks`; `no-restricted-imports` banning `lodash` and `../` parent-relative imports (use `@/`, which app and www alias to `src/*`; design has no `@/` alias — relative imports only). The import bans are **scoped to `src/**`** — root build/config files (`vite.config.ts`, `astro.config.mjs`) legitimately use relative cross-package paths. Overlays add only package-specifics: **app** → `react-refresh`, the `utils/func.ts` `any`-escape, the `routeTree.gen.ts` ignore; **www** → ignore the generated `.astro/` dir, allow triple-slash refs in `.d.ts`; **design** → no overlay rules (`.storybook/*` sits outside `src/`, so the `../`-ban doesn't reach its relative `design.css` import). www lints its `.ts`/`.tsx` (React islands + data); `.astro` files aren't linted (would need `eslint-plugin-astro`).
**Invariants.** ⚠️ Only `react-refresh/only-export-components` warnings are left standing (on purpose). New **errors** must be fixed or explicitly ruled.
**Gotchas.** ⚠️ The repo root hoists eslint **8.57.1** (eslintrc-era, chokes on flat config); each package resolves its own nested **9.x**. Run lint via `-w` or from inside the package (`npm run lint -w packages/app`), never the root binary.
**Example.** _None._
