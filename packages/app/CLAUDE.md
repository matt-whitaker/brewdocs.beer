## Layering: `design` → `component/` → `screen/`
**Purpose.** Three layers, and the boundary between them is **what a file is allowed to know**. Ask this before the subsystem sections below: they say how a thing works, this says where it goes.
**Where.** `packages/design/src/components/` (primitives) → `src/component/` (app-wide display + behaviour) → `src/screen/` (one per route, tab or modal).
**How it works.**
- **`design`** — primitives. Props in, class strings out. Knows nothing of batches, recipes or the kb; if what a prop means can only be said in brewing terms, the primitive is holding someone else's knowledge.
- **`component/`** — composes primitives into app-shaped UI and owns **interaction** state: which tab is showing, whether a disclosure is open, the half-typed value in a field, clearing it after a confirm. It is told what to render and what to call; it does not decide what is true.
- **`screen/`** — reads the store, computes, decides policy, and hands the answers down as plain props. The only layer that may know what a batch is.

⚠️ **The test: if answering the question needs the domain — what a batch is, which reading kinds a phase allows, whether anything is left to check off — it belongs in `screen/`.** If it is only about what the user is currently doing to the UI, it belongs to the component. Depth of a file is not the measure; a 200-line component that only renders is correctly placed, and a 20-line one that decides is not.

**Invariants.**
- ⚠️ **Never infer a capability from prop presence.** `available.ingredients = !!onQuickSchedule && !!scheduleKindOptions?.length` reads as "the caller passed a handler, so the brewer must have ingredients left" — a domain fact arriving implicitly through the shape of the props. The screen knows the answer outright, so pass it. Inferred this way it cannot express *available but empty*, and the caller cannot see that anything was decided.
- ⚠️ **Precedence, fallbacks and the copy around them are policy, not layout.** Which tab opens when several are available, which wins when none are, and what the disabled one says on hover are product decisions — they read as arrangement and are not.
- ⚠️ **A component may hold draft state; it may not decide what the draft means.** Per-tab `kind`/`value`/`parameter` are interaction and belong to the component. `valueLabel && typed ? typed : undefined` — ruling that a typed value is meaningless for the selected kind — is the domain.

**Gotchas.** ⚠️ **This drifts silently because a misplaced file works.** It passes the gate, renders correctly for its one caller, and surfaces only when a second caller needs the decision made differently — at which point the component grows a prop to switch on it and the layer is negotiating rather than rendering. Same failure mode as `src/actions/`, which collected three live-only files before _Actions_ stated its membership test; a layer without a stated test accumulates whatever compiles.
**Example.** `packages/design/src/components/brew-timer/quick-action.tsx` is the standing case, and it is **two** layers off rather than one: the availability inference, the tab precedence with its `unavailableTitle` copy, and the value-meaningfulness rule all sit in **design**, which may know no brewing domain at all. Its form state is right; every decision listed above is not. Correcting it means the screen passes the available tabs and the active one outright, and the primitive renders what it is given.

## Routing
**Purpose.** File-based routing (TanStack Router) with a generated route tree.
**Where.** `src/routes/*` — routes `/`, `/batches`, `/batch/$batchId`, `/recipes`, `/recipe/$recipeId`, `/recipe/$recipeId_/edit` (delisted, nothing links to it), `/knowledge`, `/disclaimer`, `/migrations/failed` (unlisted, nothing links to it — see #714). `routeTree.gen.ts` (generated); `main.tsx` (`defaultErrorComponent` renders thrown suspense-fetch errors).
**Invariants.** ⚠️ Never hand-edit `routeTree.gen.ts` (the router Vite plugin regenerates it). Read path params via `Route.useParams()`.
**Gotchas.** ⚠️ Param filenames contain `$` (`batch.$batchId.tsx`) → the shell expands it, and under the `@claude` permission layer that's rejected as "shell expansion syntax in paths". Quote just the dollar: `git rm packages/app/src/routes/recipe.'$'recipeId.tsx`. Retrying with different outer quoting will not work.
**Example.** Rename a param route → write the new file, then `git rm` the old with the `'$'` escape above.

## Breadcrumbs (the page "title")
**Purpose.** A route-owned breadcrumb trail rendered once at the top of every page — it **is** the page title, so screens don't render a redundant heading.
**Where.** `component/breadcrumbs/` — `context.tsx` (context + `useBreadcrumbs`/`useBreadcrumbTrail` hooks + the `dynamicCrumb` factory), `index.tsx` (the `Breadcrumbs` component **and** `BreadcrumbProvider` — the Provider lives here, not in `context.tsx`, so that file stays Fast-Refresh-clean). Mounted in `routes/__root.tsx`: `<BreadcrumbProvider>` wraps the shell, `<Breadcrumbs/>` sits above `<Outlet/>`.
**Surface.** `useBreadcrumbs(crumbs: Crumb[])` — registers a group while the caller is mounted. A `Crumb` is either static (`{label, to?, params?}`) or dynamic (built via `dynamicCrumb(hook, args, transform, rest?)`). `to`/`params` make a crumb a `<Link>`.
**How it works.** Each route calls `useBreadcrumbs` with its own trail; groups accumulate in a `Map` and `useBreadcrumbTrail` flattens them **reverse of registration** (effects fire child-first, so reversing yields parent→child). A **dynamic** crumb defers its data hook into a `<Suspense>`-wrapped label *inside* `Breadcrumbs` — never in the route, so the route itself can't suspend on a name lookup. Pass the hook **by reference + args** (`dynamicCrumb(useRecipeResource, ["user", id], r => r.name)`), not a `() => useX()` thunk (rules-of-hooks).
**Invariants.**
- ⚠️ Pass a **stable** `crumbs` array — a module `const` for a static trail, `useMemo` keyed on the route params for a dynamic one. It drives an effect; a fresh array each render thrashes.
- ⚠️ The container's `shrink-0` and `overflow-y-hidden` classes are **both load-bearing** (see Gotchas) — don't drop them.
**Gotchas.** ⚠️ `DrawerContent` is a fixed-height (`h-full`) flex column whose children overflow it, so **without `shrink-0`** flexbox squeezes the breadcrumb box *below its content height*, and the squeeze varies with the active panel's height → the tab bar wobbles ~1px on tab switches. **`overflow-y-hidden`** cancels the stray vertical scrollbar daisyui's `.breadcrumbs { overflow-x:auto }` otherwise induces on mobile. `/` (home) and `/disclaimer` are **intentionally exempt** — they register no crumbs (home is the hero landing; disclaimer keeps its own `<h1>`).
**Example.** `recipe.$recipeId_.edit.tsx`: `useMemo<Crumb[]>(() => [{label:"Recipes", to:"/recipes"}, dynamicCrumb(useRecipeResource, ["user", recipeId], r => r.name, {to:"/recipe/$recipeId", params:{recipeId}}), {label:"Edit"}], [recipeId])`.

## State (TanStack Query, suspense-first)
**Purpose.** All reads go through suspense wrapper hooks; nothing refetches on its own.
**Where.** `src/state/*` — `useBatches`/`useBatch`; **local editable recipes** `useRecipes`/`useRecipe`/`saveRecipe` (`recipes.ts`, backed by the `recipes` store); **read-only KB catalog** `useKbRecipes`/`useKbRecipe` + `fetchKbRecipe` (`kbRecipes.ts`) + `useKbGrains/Hops/Yeasts`; `useSession`, `query-params`. `queryClient.ts`. ⚠️ The two recipe families are distinct: `useRecipe` reads a user-owned `Recipe` from IndexedDB, the kb hooks read catalog `KbRecipe`s — don't cross them. Screens that need one catalog recipe by id currently go through `useRecipeResource`/`useBatchRecipe` (`state/disambiguation.ts`, backed by `fetchKbRecipe`) instead of `useKbRecipe` — `useKbRecipe` has no call site today but is kept deliberately for future use, not dead code (same treatment as `utils/func.ts`'s unused exports — see _Editing pattern_).
**How it works.** Wrapper hooks use `useSuspenseQuery`, return non-null data, throw on failure; screens wrap them in `<Suspense>` at the route level. All four kb resources are prefetched at boot (`main.tsx`).
**Invariants.** ⚠️ `queryClient` sets `staleTime: Infinity` — every write must explicitly `queryClient.invalidateQueries(...)` (`saveBatch`, `saveSession`, actions in `src/actions/`).
**Gotchas.** Stale data after a mutation ⇒ a missing invalidation is the first suspect.
**Example.** _None._

## Offline-first kb data flow
**Purpose.** Serve kb data from a local IndexedDB cache, hydrating from HTTP on first miss.
**Where.** `src/storage/kb.ts`, the `useKbX` hooks.
**How it works.**
```
useKbX() → IndexedDB hit? return it
         → miss + offline?  throw (rendered by the router error component)
         → miss + online:   importResource() over HTTP → hydrate IndexedDB → return
```
**Invariants.** _None._
**Gotchas.** ⚠️ The local kb cache has **no versioning** — a changed stored shape yields stale data until purged. `/?purge=true` on any URL wipes batches + session + kb stores and redirects home (`component/db-cleanup`).
**Example.** _None._

## Storage (`src/storage/`)
**Purpose.** localforage wrappers for the app's persisted state.
**Where.** `forage.ts` (`Forage<T>` base; keys are `` `${name}#${id}` ``), `batches` (IndexedDB), `recipes` (IndexedDB, store name `"recipes"` — user-owned recipes, distinct from the `kb` cache's `"recipes"` resource entry), `kb` (IndexedDB, one entry per resource), `session` (sessionStorage — collapse/toggle memory, cleared on tab close), `query` + `queryStorageDriver.ts`, `localforage.ts` (driver registration).
**How it works.** `queryStorageDriver.ts` is a **custom localforage driver backed by the URL query string** — a synchronous `Storage`-shaped shim over `URLSearchParams` + `history.replaceState`, using localforage's serializer (values keep JSON types) and a `name/` key-prefix (ignores foreign params). Registered as `LF_QUERYSTORAGE`.
**Invariants.** ⚠️ Query-driver values must be small (they sit in the address bar) and JSON-serializable.
**Gotchas.** URL-backed state **survives an inline refresh but resets on navigation** (the query string is dropped) — which is exactly why the panel switcher stores the active tab there.
**Example.** _None._

## Model boundary: Kb* vs app models
**Purpose.** Two model families with a deliberate transform boundary — catalog shapes vs. batch-instance shapes.
**Where.** `src/model/` (app models: `Batch`, `Grain`, `Hop`, `Yeast`, `Scalar`…), `src/transform/` (the mappers), scalar formatting in `utils/formatting.ts`.
**How it works.** **Kb models** (`KbGrain`/`KbHop`/`KbYeast`/`KbRecipe`) are richer catalog/reference shapes; they flow through kb hooks, caches, dropdowns, and knowledge screens **untransformed**. The transform to app models happens **only at the moment of use** — picking a catalog item in a BatchPlanning dropdown (`kbHopToHop` etc., fills instance defaults like `weight: "0.0oz"`), or instantiating a **KB** recipe into a batch (`createBatch(kbRecipe, …)` → `kbRecipe*To*` mappers, preserving the recipe's real values).
**Invariants.**
- ⚠️ **Every recipe-family model carries a `__type` discriminator** — `"kbRecipe"`, `"kbRecipeTemplate"` (both stamped into the data by kb's builder) and `"recipe"` (the app's own, set by `defaultRecipe` and `kbRecipeToRecipe`). Disambiguate on it; **don't sniff for a field**. `createRecipe` used `"batchSize" in source` to tell a `KbRecipe` from a `KbRecipeTemplate`, which silently inverts the moment a template gains a `batchSize` — a field is incidental, a tag is declared.
- ⚠️ **Narrow by testing the leaf tag, not the base one.** Because `Recipe extends KbRecipe`, `KbRecipe.__type` must admit `"recipe"` (it's `"kbRecipe" | "recipe"`), so `x.__type === "kbRecipe"` narrows the *true* branch only — the else branch keeps the whole union, since a `KbRecipe` tagged `"recipe"` is never excluded. Testing the single-literal side instead (`=== "kbRecipeTemplate"`) narrows **both** branches cleanly, which is why `createRecipe` is written with the template case first. No discriminator can fix this direction: a `Recipe` *is* structurally a `KbRecipe`, so TS can never subtract `KbRecipe` from a union that also holds `Recipe`.
- ⚠️ Never map Kb → app models at download/cache time. `Scalar` convention: `{value: "9.0lb", unit: "lb"}` — the display string embeds the unit; `unit` is the parsing/fallback hint.
- ⚠️ **The brewable is the plan's single source of truth, and a phase is an *instance*, not a kind.** `BrewablePhase.id` is **required** and minted at creation everywhere (`defaultBrewable`, `kbBrewableToBrewable`, the Phases add-row) — not by `ensureBrewableIds`, which only backfills the still-optional assignment/equipment ids. An assignment points at a phase via **`phaseId`**, never a `phaseType`, which is what lets two `"boil"` phases hold different ingredients. Milestones (planned readings) hang off the phase for the same reason; only their *values* live in `batch.tracker`. Don't reintroduce a second batch-level phase list to shadow this one.
- ⚠️ **Planning's Equipment collapse state is keyed by phase position, not id.** `equipment-phase-section.tsx`'s session key is `` `recipe-edit.equipment.phase.${phase}` `` where `phase` is the section's numeric index — Ingredients' own collapse key (`phase-section.tsx`) uses `phaseId` instead. Reordering phases shows the wrong section collapsed.
- ⚠️ `useJsonEdit`'s `add(dot, value)` takes **`unknown`**, so a new brewable item missing a required field (a phase without `id`/`milestones`) type-checks fine and then fails at runtime — `liveTrackerKeys` throws, and because saves are fire-and-forget the write is **silently lost**. Type the object at the add site (`const phase: BrewablePhase = …`) so tsc catches it.
**Gotchas.**

_The three model families._

- `model/recipe.ts` — the live editable model for user-owned recipes. `Recipe extends Entity`, built on app `Scalar`/models (the editable complement to `KbRecipe`), persisted through `storage/recipes.ts` + `state/recipes.ts`.
- KB-sourced recipes flow as `KbRecipe` everywhere via `state/kbRecipes.ts`, untransformed.
- `model/brewable.ts` — `Brewable` (`schedule` + `assignments`), the structure the brew-day pilot is built on. App-local for now; the core/kb long-term home is an open question.
- `Recipe.brewable: Brewable`, `Batch.brewable: Brewable` and `KbRecipe.brewable: KbBrewable` all carry one — no derivation, all narrowing.

_Where a brewable comes from._

- `defaultRecipe` seeds a brand-new `Recipe` with `defaultBrewable()`.
- `kbRecipeToRecipe` narrows the kb data's own `kbRecipe.brewable` via `transform/kbBrewableToBrewable.ts`: loose kb strings into the app's `PhaseType`/`ResourceType`/discriminated `Assignment`, **mints a uuid per phase**, and resolves each assignment's authored `phaseType` to the id of the first phase of that type. Authored kb JSON stays type-based; the app works in phase *instances*.
- `createBatch` builds `batch.brewable` the same way — a deep clone of the recipe's own brewable for a **user** recipe, `kbBrewableToBrewable(kbRecipe.brewable)` for a **kb** one (see _Actions_).
- **The brewable is the editing source of truth** and, since #196, the *only* place a recipe's ingredients/equipment live. `saveRecipe` (`state/recipes.ts`) just persists the edited recipe; `createBatch` reads `recipe.brewable` directly.

_The editors._

- `screen/recipe-edit/` — a thin wrapper: a name/brewer header plus `BrewableEdit`.
- `screen/batch-planning/` — mirrors it, with a plain name header and no `brewDate` (a brew-day fact, not a planning one — it lives on BatchSchedule's **Prep** tab, see _BatchSchedule screen_). Drives `batch.brewable`, saving only `{brewable}`; `updateBatch` takes a `Partial<Batch>`, merges it onto the freshest stored batch, then re-derives.
- `screen/brewable-edit/` — the **reusable brewable editor**. Takes an already-loaded `brewable` plus an `onChangeBrewable` save callback (and optional `panelsBefore`/`panelsAfter`), and only ever reads/writes that brewable through one brewable-scoped `useJsonEdit<Brewable>` the panels share. Dot-paths are **relative to the brewable** (`assignments[...]`, `schedule.phases[...]`).
- The caller owns loading and persisting — `recipe-edit/index.tsx` calls `useRecipe` and saves only `{brewable}` via `patchRecipe` (a `Partial<Recipe>` read-modify-write in `state/recipes.ts`), so the sibling Details panel's other-field edits aren't clobbered. The merge happens at the store against the freshest value, no `recipeRef`.
- ⚠️ That merge protects against a **stale draft**, not against **overlapping writes** — read-modify-write is only safe if it can't interleave with another, which is what _Serialized writes_ now guarantees.
- recipe-edit injects its recipe-specific **Details** panel (`screen/recipe-edit-details/`) as `panelsBefore`. It `patchRecipe`s its own top-level fields and never writes brewable back — a late debounced save after a tab switch would otherwise overwrite a brewable edit.

_BrewableEdit's three panels._

- **Ingredients** (`brewable-edit/ingredients/`) — assignments grouped by phase **instance** (outer collapsible section, position-numbered `1. Mash`, keyed on `phase.id` like everything else here) then `resourceType` (inner subsection). ⚠️ **The add-row belongs to the resource type, not the phase** (`resource-add-row.tsx`): each subsection ends with its own, offering only that type — a catalog dropdown for grains/hops/yeasts, a freeform text field for additives, which have no catalog. ⚠️ **Which is why every subsection renders, empty or not**: the add-row is the only way to seed a type into a phase, so hiding an empty `Hops` would make a hop unaddable. The predecessor was one add-row per phase with a merged dropdown encoding `"<type>:<name>"` — so on Boil, Hops and Additives were driven by the same control, which is the bug it replaced (#735).
- `assignment-row.tsx` carries the resource-narrowed fields — grain/hop headline weight; hop alpha/boil, yeast attenuation/temp/starter, additive weight-or-boil under the row's expander. `Additive` is `{name, boil?, weight?}`, both optional so old boil-only stored additives stay valid; the row branches on which one the resource actually carries, and a new additive defaults to `weight` on a Conditioning phase, `boil` everywhere else via `defaultAdditive(name, kind)`.
- **Equipment** (`brewable-edit/equipment/`) — grouped by phase **instance** (equipment lives at `schedule.phases[i].equipment`, not a flat list): one collapsible section per phase (`phaseLabel`, e.g. `1. Mash`) with its equipment plus a per-phase add-row from `data/equipment.ts`.
- **Phases** (`brewable-edit/phases/`) — the phases as entries: add / remove / **reorder** only (up/down via `useJsonEdit`'s `move`; `canRemovePhase` blocks removing the last phase of a required type). No equipment nested here.
- ⚠️ A `BrewablePhase` carries **equipment, not step content**. The legacy `mash`/`boil` step arrays were removed rather than migrated, and a representation for step content is still to be designed — don't assume one exists.
- ⚠️ An optional **`locked`** prop (default `false`, threaded `BrewableEdit` → `BrewableEditPhases` → the row / add-row) **disables** — never hides — the add / remove / move-up / move-down controls, each carrying a `title` of *"Locked — a phase has already been completed"* (`phases/locked.ts`), so a brewer can still read what's ahead. Only **Batch Planning** sets it, as `currentPhaseIndex(batch.brewable.schedule.phases, batch.tracker) > 0` — the current-phase pointer is computed live from phase *order* plus which ids are complete (see _Live computation_), so inserting, removing or reordering phases mid-brew would make it jump. Recipe editing never locks (a `Recipe` has no tracker), and Ingredients/Equipment stay editable throughout: the rule is about the progression pointer, not phase data.

_Batch-only: per-instance ids._

- A **batch's** brewable items (assignments, phases, phase-equipment) carry a stable per-instance `id?: string`, minted by `actions/ensureBrewableIds.ts` (idempotent: `id ??= newId()`, `utils/id.ts`) in the batch **write path** — at `createBatch` and the top of `updateBatch`.
- `updateBatch` is what stamps ids onto items just added in Planning (the add-rows create items without one), so any brewable that has been saved has ids. Recipe and kb brewables never get one.
- There is no on-load id backfill — dev assumes a pristine store (see the root `CLAUDE.md`).

_Batch-only: the tracker._

- `batch.tracker: Record<string, TrackerEntry>` (`model/tracker.ts`) keys off those ids, alongside the existing `slug` (catalog identity, shared across instances — `id` is per-instance). A `Ref` (`{on: "assignment"|"equipment", id}` or `{on: "milestone", phaseId, when, kind}`) stringifies via `key(ref)` to an id-keyed entry holding brew-day overlay state: checkoffs, actuals, gravity readings, yeast pitch.
- A `TrackerEntry` has **two** bundled-value fields: `resource` (assignment actuals) and `water` (`WaterReadings` — a `Scalar` per `WaterParameter`: `ph`/`calcium`/`magnesium`/`sodium`/`sulfate`/`chloride`/`bicarbonate`), written by the `"water"` milestone kind, which records a whole water sample in one row instead of the single `reading` every other kind uses.
- ⚠️ `putEntry` merges **both** one level deeper than the rest of the entry, so patching one mineral (or one resource field) can't wipe a sibling recorded a moment earlier.
- `actions/tracker.ts`'s `putEntry`/`pruneTracker` are the only sanctioned writers — a key like `equipment:<uuid>` has colons that `utils/func.ts`'s dot-path `get`/`setIn` won't cleanly address, so tracker writes go through `useJsonEdit`'s functional `mutate` (whole-draft update) rather than a dot-path `update`.
- `defaultBatch`/`createBatch` seed `tracker: {}`. BatchSchedule's equipment checkoff (#210), post-phase gravity readings (#211), and schedule-ingredient checkoff/actual + yeast pitch date (#212, which also dropped `Batch.pitchedDate` — see _BatchSchedule_) all live there.
- Eager-pruned on every save: `updateBatch` feeds `actions/tracker.ts`'s `liveTrackerKeys(brewable)` (every current `assignment`/`equipment`/mash-or-boil post-gravity `milestone` key) into `pruneTracker`, so a ref dropped from the brewable (ingredient/equipment/phase removed in Planning) drops from the tracker too, and re-adding one mints a fresh id with no prior entry.

_Batch-only: the timer._

- `Batch.timer?: TimerEvent[]` (`model/timer.ts`) is a **second, distinct brew-day-overlay field**, deliberately not shaped like `tracker`: one **global per-batch session log**, an append-only array of `{type: "start"|"pause"|"resume"|"stop", date}` — not a map keyed by per-instance ids, and not scoped to a phase.
- ⚠️ `date` is a **real absolute ISO timestamp** (`new Date().toISOString()` at the call site), never a running duration or an offset. That is what lets a session sit paused for days and resume with no special-casing of the gap.
- Nothing accumulates a counter: `model/timer.ts`'s `elapsedSeconds(events, now)` is wall-clock time since the first `"start"` — running ⇒ `now − startedAt`, frozen ⇒ `lastEvent.date − startedAt`. ⚠️ It shares that basis with `brew-timer.tsx`'s marker `at()`; when it didn't (#422), markers logged during a pause exceeded it and `BrewTimerMarkerOverlay` silently dropped them.
- `isRunning(events)` just tests the last event, so the live counter recomputes correctly after the tab was backgrounded, or closed and reopened.
- Both are pure and tolerate `undefined` (absent or empty ⇒ never started, 0 elapsed); per _Data compatibility_ there is no backfill for older stored batches without the field.

_Versioned entities._ `Entity` (`packages/core/src/models.ts`) carries an optional `version?: number`; a stored record missing one is treated as version `1`. `storage/migration/` holds the `Migration` contract, registry and runner that carry a record forward through that chain — see _Data compatibility_ for how it wires into `Forage<T>` and which domains use it today.
**Example.** _None._

## Actions (`src/actions/`) — anything whose result is persisted

**Purpose.** An **action** is an operation whose result is **stored**: a mutation, or a computation whose output is written to the batch. ⚠️ **That is the whole membership test for this folder.** A function that computes a value which only ever exists live is not an action, however batch-shaped it is — see _Live computation_.
**Where.** `createBatch`/`createRecipe` (instantiation), `updateBatch` (the edit save path), `_updateShopping` → `batch.shopping`, `ensureBrewableIds` (mints per-instance ids in the write path), `tracker.ts` (`putEntry`/`pruneTracker`/`liveTrackerKeys`, all feeding `updateBatch`'s save). `data/defaultBatch.ts` is a **factory**, not a module-level const: a shared object gets spread into every batch by reference (`{...defaultBatch}` is shallow), so an in-place mutation of a nested field would leak across every batch made in that session.
**How it works.** `batch.shopping` is the **only persisted derivation left**, and it needs two conventions the live views do not:

- **Reuse-by-reference** — the shopping rebuild matches new items against the previous list by a stable key (`tag:name`) and preserves its *user-owned* fields (`cost`/`purchased`); when nothing it owns changed it returns the **previous object by reference** so the `isEqual` diff stays cheap. ⚠️ This machinery is only needed by a *persisted* derivation. A live view has nothing to re-attach and no stored copy to diff — don't reintroduce a reuse map for one.
- **Trigger diffing** — `updateBatch` takes a `Partial<Batch>`, merges it onto the freshest stored batch (`{...current, ...patch}`), then re-runs the shopping derivation **only when `batch.brewable` actually changed** (`isEqual` against the stored batch), since that's where the ingredients live. A `{brewDate}`-only patch, or editing the batch name, leaves brewable identical and rebuilds nothing.
- The partial-merge is what lets BatchPlanning's header and brewable editor each save just their slice without a ref (see _Model boundary_). A full-batch caller (BatchSchedule/Shopping drafts) still works — every key is present, so the merge is a straight replace.
- `createBatch` builds `batch.brewable` first — a deep clone of the recipe's own brewable for a **user** recipe, `kbBrewableToBrewable(kbRecipe.brewable)` for a **kb** one (narrowed straight from the kb data's own brewable — see _Model boundary_) — then runs `_updateShopping`.

**Invariants.** ⚠️ **Nothing lands here that isn't written to storage.** The folder drifted three times before this rule was stated, because the old section called both stored and live values "derived" and the word covered everything. ⚠️ `batch.phases` is **retired** — the BatchSchedule tabs derive from `brewable.schedule.phases` (see _BatchSchedule_).
**Gotchas.**

- ⚠️ Stored derived fields run through the migration chain when a migration exists for the shape change (see _Data compatibility_) — today that's only `batches`, whose migrations array is empty (nothing to migrate yet). A derived-field change in a domain not yet wired (recipes, etc.) still has no migration path: a stored record throws until re-derived or purged (`/?purge=true`).
- Equipment checkoff lives on BatchSchedule phases and, since #210, on `batch.tracker` (see _BatchSchedule_); the batch's second tab is `Shopping`.
**Example.** _None._

## Live computation (`src/hooks/`, pure functions in `src/model/`)

**Purpose.** Values computed on demand from the brewable and the tracker, and **thrown away** — never written back. Most of what a batch screen shows is one of these.
**Where.** Reactive views in `hooks/`: `useSchedule(brewable) → ScheduleItem[]` (called at the top of `screen/batch-schedule/index.tsx`), `useActuals(batch) → Measurements` (the Summary tab's OG/FG/ABV, from the dated `"gravity"`-kind milestone readings in `batch.tracker` — earliest by date is OG, latest is FG; returns `batch.actuals` untouched when there are none), `useEstimatedIbu`, `useElapsedSeconds`. Pure functions beside the types they read, in `model/`: `batchProgress.ts` (`currentPhaseIndex`/`batchProgress`), `timer.ts` (`elapsedSeconds`/`isRunning`), `brewable.ts` (`resourcesOf`/`indexedResourcesOf`, `phaseLabel`, `canRemovePhase`).
**Invariants.**

- ⚠️ **A reactive view goes in `hooks/`, memoized inside the hook** — not in `actions/`, and not memoized at the call site. `useActuals` and `useSchedule` are the pattern: the plain derivation stays module-private and the exported surface is a hook wrapping it in its own `useMemo`.
- ⚠️ **A pure function over a model goes in `model/`, beside its type** — `elapsedSeconds` next to `TimerEvent`, `resourcesOf` next to `Assignment`. That is not a new convention: `model/brewable.ts` has held `phaseLabel`, `canRemovePhase` and `defaultBrewable` all along. Use this when several callers need it, or when a caller isn't a component.
- ⚠️ **Don't call any of this "derived".** The word was doing double duty for `batch.shopping` (computed *and stored*) and these (computed *and discarded*), and `actions/` accumulated three live-only files along exactly that seam. Say **stored** or **live**.
- `batch.actuals` is never written by any screen, so `defaultBatch.ts`'s placeholders are only what shows before a reading exists.

**Gotchas.**

- ⚠️ Computing live is what keeps write-through paths honest. When `schedule` was persisted and only re-derived on an ingredient edit, a batch built by older code kept dead paths and a brew-day edit wrote a removed field — silently lost. A live view regenerates from the current brewable every time.
- ⚠️ A `TrackerEntry.reading` can be **present but empty** — `screen/batch-schedule/reading.tsx` writes `{value: "", unit}` both when a field is cleared and when the unit dropdown is switched on an empty reading. `useActuals`' filter checks `Number.isFinite(parseFloat(reading.value))`, not just that `reading`/`date` are set — a presence-only filter renders `NaN%`.
- Every batch view sources from the brewable: `batch-planning` edits `batch.brewable` directly via `BrewableEdit`; `_updateShopping` and `useSchedule` read ingredients from `brewable.assignments` through `resourcesOf`/`indexedResourcesOf` (the latter also surfacing each assignment's `id`); `batch-summary` goes via `organicNames`; `batch-schedule`'s equipment checklist reads `brewable.schedule.phases[].equipment` directly and live.
**Example.** _None._

## Data compatibility (versioned entities + migration)
**Purpose.** A stored record carries a version and can be carried forward through a migration chain on read, instead of a shape change either throwing until re-derived or forcing a full purge.
**Where.** `packages/app/src/storage/migration/` — the `Migration<T>` contract, a registry keyed by `entityType`, and the runner that walks a record from its stored version to the current one. `Entity` (`packages/core/src/models.ts`) carries the optional `version` the runner reads.
**How it works.** A `Migration<T>` is `{entityType, from, to, up, down}` — a plain object, callable standalone. `up` and `down` both have a caller, one version step at a time: `runner.ts` walks either direction over the same registry — `runMigrations` forward (`from === current && to > current`), `runMigrationsDown` back (`to === current && from < current`, applying `down` and stamping `migration.from`), sharing one contained walk so a throwing `down` returns a failure result exactly as a throwing `up` does. `Forage<T>.get`/`list` run the chain when the store is constructed with a migration config: a step that throws is caught, the record is written to a `Forage`-backed failure store, and it is dropped from the result (excluded/`null`) rather than re-thrown or repaired in place. `component/db-cleanup`'s purge wipes that failure store too, alongside batches/session/kb. `batches` is the reference integration, wired with an **empty** migrations array today — nothing to migrate yet, so there's no observable behavior change. `recipes`, `kb` and `session` are not wired.
**Invariants.**
- ⚠️ A stored record missing `version` is treated as version `1` ("oldest known"), not an error.
- ⚠️ **Containment, never repair, still holds.** A migration that itself throws is caught and set aside in the failure store — never retried automatically, never re-thrown into the render path. Same instinct as the graceful-degradation rule below, one layer lower: a stale or unmigratable record is allowed to fail to render, never allowed to take a screen down with it.
- A pre-migration backup **is** kept — one raw snapshot per record, written to its own `Forage`-backed backup store immediately before that record's migration chain runs, only when a migration is actually about to happen. It is not a history: each later migration on that record **overwrites** its prior backup rather than accumulating one, so at most one prior version is ever retrievable per record — a deliberate bound on storage growth that needs no pruning job. `component/db-cleanup`'s purge wipes it too, alongside the failure store.
- ⚠️ **Reverting is one entry point, `state/migrationBackups.ts`'s `revertMigrationBackup`, and a caller never picks the mechanism.** It prefers the snapshot — writing `backup.data` back byte-for-byte — whenever the stored record is still at the backup's `toVersion`, and otherwise walks `runMigrationsDown` from the record's real version to `backup.fromVersion`, which is only as faithful as the migration author's `down` (see `packages/spec/product/reverts.md`, REVERTS-03/04). `revertKindFor` answers which of the two a given backup would get, for a UI that has to say so before the brewer commits. The backup is **deleted** once it has been used: the migration it describes has been undone, so the record no longer sits at its `toVersion` and the snapshot would only offer a revert to a level the record is already at. A record absent from its store is not revertable — there is nothing to revert, and no version to compare against. Only `batches` is wired here, same as the failure store, and no screen reads any of it yet (that's #910).
- Per-instance brewable ids are still minted only in the batch **write path** (`ensureBrewableIds` at `createBatch`/`updateBatch`) — that's instance creation, not migration (see _Model boundary_).
- ⚠️ **Graceful degradation is still the requirement**, independent of the framework above: nothing contains a render throw except the router's `defaultErrorComponent`, which replaces the **whole page**, so one legacy row in a list wipes out the tab bar and every unrelated item beside it (#365: a recipe predating `targets`). Anything that maps stored records into a list contains each row — `screen/recipe-list/` wraps every `RecipeListItem` in `component/error-boundary` with an inert `RecipeListItemFallback`, keyed `` `${source}:${id}` `` so a boundary that has tripped isn't reused for a different recipe when the search filter reorders the list.
- A set-aside record isn't only silently dropped: a brewer (or whoever's helping them) can see and act on it at `/migrations/failed` — see `packages/spec/product/updates.md`.
- ⚠️ Three dev-only fixture entity types — `migration-fixture` (a v1→v2→v3 happy path), `migration-fixture-throws` (a migration that throws), `migration-fixture-orphan` (no bridging migration) — exist purely to exercise this framework end to end, since `batches`'s own migrations array is still empty. Each is a small `Forage`-backed store in `storage/migration/` (the same one-liner shape as `MigrationFailuresStorage`/`MigrationBackupsStorage` in `failures.ts`/`backups.ts`), registering its own `Migration<T>`s (or none, for the orphan case), joining `pass.ts`'s `migratedStores` only under `import.meta.env.DEV`. They never ship: `import.meta.env.DEV` compiles to `false` and Vite dead-code-eliminates the gated branch in a production build — verified by grepping `packages/app/dist/assets/*.js` for the three entity-type strings, not by trusting "should". Adding a new scenario is the same shape: register a `Migration<T>` for a new `entityType` (or omit one, for an orphan case), add its store, add it to `pass.ts`'s dev-only branch.
**Gotchas.** ⚠️ Only `batches` is wired — a shape change in `recipes`/`kb`/`session` still has no migration path and behaves as before: a stale record throws until re-derived or the store is wiped with `/?purge=true` (`component/db-cleanup` wipes batches + session + kb and redirects home).

## BatchSchedule screen: configurable phases
**Purpose.** A schedule screen driven by `phases` (config), `schedule` (derived), and the brewable's own equipment kit (derived live, checked off through the tracker).
**Where.** `screen/batch-schedule/` — `index.tsx` + `item-row.tsx` + `equipment.tsx` + `reading.tsx` (the old per-step screens were deleted). Model commentary in `model/batch.ts`.
**How it works.**
- **One sub-tab per `brewable.schedule.phases[]` entry** (the `compact` _PanelSwitcher_), titled by `phaseLabel` (`"2. Boil"`) and keyed by `phase.id`. ⚠️ `batch.phases` is **gone**: the brewable is the plan's single source of truth, so a second Boil phase is its own tab with its own ingredients, equipment and readings — never merged into the first. Collapse state keys off `phase.id`, not a renamable name. A leading **"Prep"** tab (a static `PanelSwitcherContent`, sibling to the `.map()`-produced phase tabs, not wrapped in a Fragment) holds the brew-day `brewDate` and `packaging` fields — neither is phase-derived, so they carry no number prefix and never route through `phaseLabel`; the default tab stays the first phase (`phaseLabel(…, 0)`), not Prep. `packaging?: "keg"|"bottle"` (`model/batch.ts`) is a batch-only brew-day fact, not part of `Brewable`/`Recipe` — a recipe doesn't know how a given batch will be packaged — edited via a plain `allowNull` `DataGridSelect`/`update("packaging", …)`, same shape as the Status row.
- **The schedule** — a **live view**, not a batch field: `hooks/useSchedule.ts`'s `useSchedule(data.brewable)`, called at the top of the component and memoized internally, keyed on `brewable`, each item carrying its source assignment's `id`, its **`phaseId`** (the phase instance it belongs to) and a `kind`; a tab shows the items whose `phaseId` matches it, grouped by `kind` under collapsible headers. `batch.schedule` as *storage* is gone — same treatment equipment and gravity already had.
- **Equipment** — no longer a batch-owned copy (#210 retired `Phase.equipment`/`_projectBatchBrewable`). each tab reads its **own** phase's `equipment` directly (`phase.equipment`) — no type-matching or flat-mapping across phases — the same kit BatchPlanning's `BrewableEdit` equipment panel manages, so an add/remove/rename there shows up here immediately, id-stable (`ensureBrewableIds`). `equipment.tsx` reads each item's checked state from `batch.tracker[key({on:"equipment", id})]?.completed` and calls `onToggle(id)`; `index.tsx`'s `toggleTrackerCompleted(ref)` (shared with the ingredient rows' checkoff — `toggleEquipment` is a thin wrapper over it) computes the next tracker via `putEntry` inside `useJsonEdit`'s functional `mutate` (a tracker key isn't dot-path addressable — see _Model boundary_ / _Editing pattern_), saved **immediately** (`mutate(fn, true)`), like the old checkbox's `toggle()` did, just through the tracker instead of a `phases[].equipment[].completed` write.
- **Ingredient checkoff/actual + yeast pitch (#212)** — `item-row.tsx`'s `BatchScheduleItemRow` computes its own ref (`{on:"assignment", id: item.id}`) from the row's `id`. `completed` reads `entry?.completed` (`entry` is `batch.tracker[key(ref)]`, passed down by `index.tsx`) and its checkbox calls `onToggle(ref)` → `toggleTrackerCompleted` (immediate, like equipment). `actual` reads `entry?.actual` and writes via `onPatch(ref, {actual})` → `index.tsx`'s `patchTracker` (debounced `mutate`, mirroring the reading rows below — see _Model boundary_). The yeast row's pitch date is an `extra: ScheduleDetail` with no `path` (tracker-backed instead of dot-path-backed); it reads `entry?.date` and writes via the same `onPatch(ref, {date})`, so each yeast assignment tracks its own pitch date. `hooks/useSchedule.ts` maps assignments 1:1, taking each row's `id` and `phaseId` straight off its assignment; the old `phase:kind:name` `keyer()` re-attachment key is gone — `id` is already unique and rename/reorder-stable.
- ⚠️ **Creating a reading is ONE `mutate`, never `add` then `onPatch`.** It writes two places — the `Milestone` on the brewable and its value in the tracker — and `useJsonEdit` assigns `stateRef.current` **during render**, not inside the setter. Two successive editor calls in one handler therefore read the *same* stale draft and the second silently discards the first, which is the fire-and-forget write-loss this repo keeps rediscovering. `reading.tsx`'s add row and `brew-timer.tsx`'s quick-add both build the phase array and the tracker entry inside a single `mutate(draft => …, true)`.
- ⚠️ **A reading kind is a row in `screen/batch-schedule/reading-kinds.ts`**, not a call site. `READING_KINDS` holds every kind's labels, unit options, phase gating and `primary` — where its value is written: `"reading"` (gravity/volume/temperature/pressure), `"date"` (kegDate/bottleDate, which is what sets `dateOnly`), or `"waterParameter"` (water, whose value is one of seven `WaterParameter`s and which therefore renders `BatchScheduleWaterReading` instead). `readingKindsForPhase(type)` does the gating; an absent `phaseTypes` means every phase. `WATER_PARAMETERS` lives here too — water's seven measurements, which is why its value can't be captured in the grid add row (no sensible default among seven) and is instead chosen from a dropdown in the quick-reading modal. ⚠️ `brew-timer.tsx` reads this same table; it used to carry a second, near-identical `QUICK_MILESTONE_KINDS` that silently omitted water. `index.tsx` maps over the result, so **adding a kind is a new row** — it used to be a copy-paste of five props into a 100-line JSX block, seven times over.
- **Readings (milestones)** — `reading.tsx`'s `BatchScheduleReading` is a **kind-aware** component, instantiated once per `MilestoneKind` (today `"gravity"`, `"volume"`, `"temperature"`, `"pressure"`, `"kegDate"`, `"bottleDate"`) at the bottom of each phase's panel in `index.tsx`, each with its own `unitOptions`/`headerLabel`/`addLabel`/`defaultLabel` (a module-level const per kind, e.g. `GRAVITY_UNIT_OPTIONS`).
  - All instances read/write the same `phase.milestones[]` array; each renders only the entries whose `milestone.kind` matches its own `kind` prop, so several kinds coexist on one tab as independent grids. ⚠️ Each milestone is paired with its **real index in the unfiltered array** first — that index is what the `update`/`remove` dot-paths address.
  - `onAdd` mints a `Milestone` with `label: defaultLabel`, which differs per kind (gravity `"Reading"`, volume `"Volume"`, temperature `"Temperature"`) precisely so a fresh milestone of each kind on one tab gets a distinct accessible name.
  - `"pressure"`/`"kegDate"`/`"bottleDate"` are **gated to a `phase.type`** — `index.tsx` renders them only on the carbonation/conditioning tab. Gravity, volume and temperature stay unconditional on every tab.
  - `"kegDate"`/`"bottleDate"` are the **date-only** kinds: `BatchScheduleReading`/`BatchScheduleReadingItem` take a `dateOnly` flag that skips the reading/unit inputs and renders the date field (normally behind the row's expander) as the row's primary control, so that `TrackerEntry` only ever gets a `date`, never a `.reading`.
  - `"water"` is the **bundled** kind, and lives in its own component (`water-reading.tsx`'s `BatchScheduleWaterReading`) rather than another `BatchScheduleReading` instance: one row is one water *sample*, so its expander holds a nested grid of seven parameter fields (pH + calcium/magnesium/sodium/sulfate/chloride/bicarbonate, in the module-level `WATER_PARAMETERS` const with a **fixed unit each**, hence no unit dropdown) writing into that single milestone's `TrackerEntry.water` — not a `reading`, and not one milestone per parameter.
  - ⚠️ Each water field patches only its own parameter and relies on `putEntry` merging `water` one level deep (the same protection `resource` gets), so recording sulfate can't wipe the chloride typed a moment earlier. The parameter field is memoized separately from the row, for the same reason typing in one schedule column doesn't re-render its siblings.
  - It is also gated to `phase.type === "mash"` — the carbonation/conditioning gates were the precedent, but this one is the mash tab's alone.
- ⚠️ **A phase completion records `date`, and the brew timer reads it.** `completePhase` writes `{completed: true, date}` — the timestamp is what lets `screen/batch-schedule/brew-timer.tsx` place the completion on the *global* timeline, whose markers are offsets from the session's `start` event. That marker memo walks **both** each phase's `milestones` and its own `phase` tracker entry; missing either half leaves the timeline silently short a marker, and from the UI a missing `date` and an unread entry look identical. Phases completed before this recorded no `date` and simply never appear — no backfill, per _Data compatibility_.
- **Phase completion (the batch's real progress)** — `complete-phase.tsx`'s `BatchScheduleCompletePhase` renders a **"Complete `<phaseLabel>`"** button (`aria-label` the same string) behind a `Modal`/`useModal` confirm (`This can't be undone.`, the same body the list rows' delete `Action` renders). ⚠️ It is the **first** child of the phase panel — above the equipment checklist, the ingredient grids and the reading grids — because completing the phase is the screen's primary action and a real phase's content is a long scroll (#375). Its `pt-1 pb-3` is tuned for that position: the panel wrapper's own `pt-2` sits above it, and the `pb-3` is what separates it from the first grid. Confirming calls `index.tsx`'s `completePhase`, which writes `putEntry(tracker, {on:"phase", id: phase.id}, {completed: true})` through `mutate(fn, true)` — **immediate**, like the equipment/ingredient checkoffs. The button renders **only** on the phase whose index equals `currentPhaseIndex(brewable.schedule.phases, tracker)` (`model/batchProgress.ts`), computed in its own `useMemo` — deliberately *not* folded into the `panels` memo, whose deps are `[data.brewable, schedule]`: a checkoff writes only `data.tracker`, so `data.brewable` (and the `schedule` derived from it) stays put and `panels` doesn't re-derive.
- **The Global Brew Timer** — `brew-timer.tsx`'s `BatchScheduleBrewTimer` mounts design's `BrewTimer` at the very top of the `<Screen>`, **above** the `PanelSwitcher`, so it stays visible on every phase tab; `index.tsx` hands it only `batch={data}` and the `useJsonEdit` `mutate`, keeping the timer's glue out of the screen. **Play/pause** appends to `Batch.timer` (the session log — see _Model boundary_) via `mutate(fn, true)`, immediate like the checkoffs: `isRunning(d.timer)` picks the next event, `"pause"` when running, `"resume"` when the log is non-empty, `"start"` on a first press. It's an array append driven by current state, so it can't be a dot-path `update` — same reasoning as the tracker writes. **The live counter** is `hooks/useElapsedSeconds.ts`, which re-derives `elapsedSeconds(events, new Date())` from the stored absolute timestamps on a 1 s interval **plus** `visibilitychange`/`focus`, and never accumulates in memory — a PWA tab gets backgrounded and its interval throttled or stopped, so the counter must be able to jump forward on refocus. The interval only runs while the timer is running; the resync-on-`events`-change fires either way.
  - **The quick-action tabs are wired from `model/scheduleProgress.ts`, and the screen states availability rather than letting the modal guess.** `incompleteAssignments` gives the Ingredients options, `incompleteEquipment` the Equipment options — both lists of what is *left on the current phase*, in brewing order; `quickActionTabs` carries each tab's `available` plus the reason it is not. ⚠️ **The reasons are brewing statements** ("Nothing left to add on this phase") and so cannot live in design — that is the whole point of the prop. Before this, availability was inferred inside the primitive from whether a handler had been passed, app passed none, and both tabs were dead from #629 until #651 while rendering exactly as they would if the phase were finished.
  - ⚠️ **Both tabs NAME their item; neither resolves one.** There is deliberately no "next incomplete" resolver for either. Equipment never had an order; ingredients only *look* like they do — hops are chronological by boil time, but grain goes into the mash all at once and an additive may or may not carry a boil time, so a resolver is right for one kind and an arbitrary pick dressed as a resolution for the other two (#663). The list is offered in brewing order with the first preselected, so working down a boil is still one confirm per addition — the speed comes from the ordering, not from deciding for the brewer.
  - ⚠️ **The option label is the screen's to build, and it carries the boil time** (`` `${name} · ${boil.value}` ``) precisely because three additions of one hop are otherwise three identical entries a brewer cannot tell apart. design never parses a name; it renders what it is given. `QUICK_SCHEDULE_KINDS` maps a `ResourceType` to the **one** `ResourceScalarField` a quick check-off records (grain/hop/additive `weight`, yeast `temp`) and its label, keyed per option id — a type with no `valueLabel` (yeast) shows no value field.
  - **Quick milestone** reuses `reading.tsx`'s mint-and-track pattern (a `Milestone` on the phase + a `{on:"milestone", id}` tracker entry), so the reading lands in that phase's own reading grid rather than a parallel timer-only record. ⚠️ It does both in **one** `mutate`, not `add()` then `mutate()`: `useJsonEdit` reads the draft through a ref that only refreshes on render, so within one handler the second call still sees the pre-`add` draft — the milestone would be dropped, and `updateBatch`'s eager-prune would then bin the now-orphaned tracker entry. Any two-part edit to one draft has this hazard; put it in a single `mutate`.
  - ⚠️ The entry it writes is a **full ISO timestamp**, because the marker offset is `(entry.date − sessionStart)` in seconds and a date-only string can't carry that. Every other writer of `TrackerEntry.date` is an `<input type="date">` (date-only), which renders an ISO timestamp as blank — hence `reading.tsx`'s date inputs display `entry.date.slice(0, 10)`. Editing that field writes the date-only value back and the milestone drops off the chart (its offset goes negative and `BrewTimerMarkerOverlay` filters it), which is the accepted trade for now.
  - ⚠️ **A marker's `offsetSeconds` and the timer's `elapsedSeconds` are compared directly, so both must round the same way — down.** `BrewTimerMarkerOverlay`'s `place()` hides anything with `offsetSeconds > elapsedSeconds` (its job is to keep markers from running off the end of the line), and `elapsedSeconds()` floors. `brew-timer.tsx`'s `at()` therefore floors too. It used to `Math.round`, so a marker recorded at a true 3.6 s got offset `4` while the display still read `3` and stayed invisible for up to two more ticks (~2.3 s measured) — a lag whose size was decided by the fraction of the second the brewer happened to click in, which read as random. Changing the rounding on **either** side alone reintroduces it, for phase completions and quick-logged milestones alike (both go through `at()`).
  - `BrewTimer`'s Global/Phase toggle (`scope`, local state, default `"global"`) picks both the counter and the `markers` memo. Global is **all** milestones across **all** phases whose tracker entry has a parsable `date`, offset from the first `"start"` event, floored. Phase instead returns only the active phase's own milestones plus its completion marker, offset from `phaseStartDate(phases, currentIndex, batch.tracker, batch.timer)` (`model/batchProgress.ts`) rather than session start; both branches build their markers through one `markersOf` helper so a phase completion is handled identically either way.
  - ⚠️ **Phase offsets exclude paused spans, and that has to match the counter they sit beside.** `elapsed` is two independent `useElapsedSeconds(batch.timer, since?)` calls — `globalElapsed` (no `since`, unchanged) and `phaseElapsed` (`since` the phase boundary, which makes the hook tick `runningSecondsSince` instead of `elapsedSeconds`) — and `scope` only picks which one reaches `<BrewTimer elapsedSeconds=…>`, so switching to Phase and back always returns Global to true wall-clock time. A Phase marker's offset uses that same `runningSecondsSince`, filtered to timer events at or before the marker; a wall-clock offset against a pause-excluding counter would put `offsetSeconds` past `elapsedSeconds` and `BrewTimerMarkerOverlay` would silently drop the marker — the #422 failure again.
  - `milestoneKindOptions` come from the module-level `QUICK_MILESTONE_KINDS` table, which mirrors index.tsx's per-kind `defaultLabel`s and the `phase.type` gates on `pressure`/`kegDate`/`bottleDate` — ⚠️ but the modal picks kind and phase **independently**, so a gated kind is offered whenever *any* phase of that type exists and can be filed onto a phase whose tab doesn't render it. It's still a real milestone in the data; it just has no grid to show it.**Invariants.**
- ⚠️ **One order governs the panel and the quick action, and it is brewing order** (`byBrewingOrder`, exported from `model/scheduleProgress.ts` and used by both `index.tsx`'s panel sort and `nextIncompleteAssignment`). Boil-timed additions sort longest-boil first — the boil is a countdown, so that *is* chronological — and everything without one keeps the order the brewer arranged in Planning, which the sort's stability preserves. ⚠️ **Planning is never re-sorted**: arranging ingredients is a decision the brewer makes, and only the brew-day panel imposes an order on it. The panel used to sort by `name.localeCompare` while the resolver walked brewing order, so the quick action ticked a row the brewer had not chosen — the second one shown, with nothing to explain it (#656). Changing either sort alone reintroduces that; they are one function for that reason.
- ⚠️ **The active phase tab persists by label, not id.** `usePanelSwitcher` stores the panel's `title` (`phaseLabel`, e.g. `"2. Boil"`) as the query-param value and matches it back by exact string — the React key and the collapse-state key above are both `phase.id` and stay stable. `phaseLabel` renumbers on reorder (`model/brewable.ts`), so reordering desyncs the stored active tab and no tab shows selected until one is picked again.
- ⚠️ **The brew-day screen never edits the plan.** Every editable value on a schedule row is **tracker-backed**, and the as-brewed values mirror the plan's own shape: `TrackerEntry.resource` is a `ResourceActuals` (`Partial<Omit<Grain & Hop & Yeast & Additive, "name">>`) keyed by the **same field names** as `assignment.resource` — a hop records `resource.weight`/`resource.boil`, a yeast `resource.temp`. `date` is universal (pitch date, reading date) and `reading` is milestone-only — shared by every `MilestoneKind`, not gravity-specific. `ScheduleItem` carries the *planned* `resource` read-only plus its `resourceType`; the screen's `COLUMNS` const maps a resource type to the fields worth a column, and each column reads plan and actual from the **same key**, so adding e.g. `"alpha"` for hops needs no model, tracker or derivation change. A row shows the plan until an actual is entered, then notes each drift (`(7.4% · plan 1.0oz · plan 60min)`). The old `path` dot-path write-through into `brewable.assignments[i].resource.*` is **gone** — editing the plan is Planning's job; doing it from here overwrote the recipe-derived intent with no record of it. Grains have no secondary value (checklist + amount only).
**Gotchas.** ⚠️ `putEntry` merges `resource` **one level deeper** than the rest of the entry — each column patches its own field, so a plain spread would let recording a boil time silently wipe a weight recorded a moment earlier. `ScheduleItem.resource` is the derived plan; `TrackerEntry.resource`'s fields are set only when what happened differed — capturing brew-day facts *without* rewriting the plan the shopping list aggregates from. `extra: ScheduleDetail[]` are secondary fields (e.g. pitch date) behind the row's expander — a field, not a step; all of them are tracker-backed now, so `ScheduleDetail` has no `path`. `assignment:<id>`/`equipment:<id>`/`milestone:<id>` tracker keys for a brewable item removed in Planning are dropped on the next save (`updateBatch`'s eager-prune — see _Actions_), not immediately on the edit itself.
**Example.** _None._

## Editing pattern (`hooks/useJsonEdit.ts`)
**Purpose.** The workhorse for draft editing — local draft + dot-path updates + debounced saves. Generic over any object (`<T extends object>`): a whole `Entity` (Batch/Recipe) or a sub-object like a `Brewable` (what `BrewableEdit` edits, merging it back onto the recipe on save).
**Where.** `hooks/useJsonEdit.ts`; dot-path `get`/`set`/`setIn` in `utils/func.ts`.
**How it works.** Local draft state; `update("hops[0].boil.value", v)` dot-path writes; **350 ms-debounced** saves; `updateScalar` re-formats on blur using the **previous scalar's unit** as the default when the user types a bare number. Editors read the draft through a ref so their identity stays stable across edits (memoized rows don't re-render). Paths support dot and bracket segments. The returned tuple is `[data, update, updateScalar, toggle, add, remove, move, mutate]` — `move(path, from, to)` is a bounds-checked swap backing the Phases panel's reorder controls; `mutate(fn, immediate?)` is a **functional whole-draft update** (`fn(latestDraft) => nextDraft`) for edits a dot-path can't express — e.g. a map keyed by `"equipment:<uuid>"`, whose colons aren't dot-addressable. Because `mutate` reads the freshest draft through the hook's own ref, a consumer no longer needs its own `useRef` to avoid a stale closure while keeping a stable callback (this is how BatchSchedule's tracker toggles dropped their `dataRef`).
**Invariants.** ⚠️ Uses hand-rolled `utils/func.ts`, **not lodash** — don't add lodash (now lint-enforced). ⚠️ `utils/func.ts` is a deliberate mini-stdlib, so some of its exports have **no call site yet** (`set` — the mutating twin of `setIn` — plus `intersection` and `pipe`). That's intentional surface, **not** dead code: leave them. The resync effect deep-compares before accepting store emissions, so a re-emitted identical batch doesn't disturb an in-progress draft. ⚠️ **It also skips entirely while an edit is pending** (`pending` ref, set on `commit`, cleared when the save actually settles). A deep-compare only rejects an *identical* emission; a **different** one — the store's own echo of a sibling save — was accepted mid-keystroke and replaced the draft, so the debounced save that followed wrote from a draft that had already lost those keystrokes. That is half of #455; the other half is that the writes themselves interleaved (see _Serialized writes_). Neither fix alone closed it: `recipe-edit.spec.ts:108` went 0/3 → 4/5 with serialization alone, and only 8/8 with both.
**Gotchas.** _None._
**Example.** `update("hops[0].boil.value", v)`.

## Serialized writes (`utils/serialize.ts`)
**Purpose.** One writer at a time per stored entity, so a read-modify-write can't interleave with another and lose the earlier edit.
**Where.** `utils/serialize.ts` — `serialize(key, task)` chains each task onto a promise held per key. `state/recipes.ts`'s `patchRecipe` uses `recipe:<id>`; `actions/updateBatch.ts` uses `batch:<id>`.
**How it works.** The chain survives a rejected task (`previous.then(task, task)`), and the map entry is deleted once its chain drains, so it doesn't grow per id forever.
**Invariants.** ⚠️ **The whole read-modify-write goes inside the task**, not just the read — `updateBatch` derives shopping and prunes the tracker between them, and those read `current` too.
**Gotchas.** ⚠️ Both write paths were plain read-merge-write, and two saves in flight for the same id would both read the pre-write value; the second `{...current, ...patch}` then clobbered the first. Reachable from any screen with two writers — recipe-edit's Details and Ingredients panels, and Shopping's immediate checkbox next to its debounced cost field. It is **not** enough on its own: the draft-level half is `useJsonEdit`'s resync (see _Editing pattern_). Measured on `recipe-edit.spec.ts:108`: 0/3 passing before, 4/5 with serialization alone, 8/8 with both.
**Example.** `serialize(`batch:${id}`, async () => { … })`.

## PanelSwitcher (`component/panel-switcher/`)
**Purpose.** A fully React-controlled tablist/tabpanel (button tabs, not DaisyUI's radio+CSS pattern) that mounts **only the active panel**.
**Where.** `component/panel-switcher/` (`usePanelSwitcher` drives it). Consumers declare panels as direct children: `<PanelSwitcher name="batch" defaultTab="Planning"><PanelSwitcherContent title="…">…` (the batch tabs are Planning / Shopping / Schedule / Summary).
**How it works.** `PanelSwitcherContent` never renders; `PanelSwitcher` reads its props via `React.Children`. Tab switches run inside a `useTransition`. A `compact` prop gives tighter tabs (`tabs-sm`, in-flow not mobile-full-bleed) for a nested sub-nav — used by BatchSchedule (one sub-tab per phase) and BatchPlanning (`Ingredients`/`Equipment`/`Phases`). Unmount-on-switch is safe because edits persist through debounced saves and UI state persists (collapse → `session`, active tab → `query`).
**Invariants.**
- ⚠️ Panels must be **direct children** — a `.map()` array is fine (`Children.toArray` flattens it), but a **wrapping Fragment is not** (it collapses to one child and the tabs vanish). A panel with no children renders as a disabled tab.
- ⚠️ The tablist sits **outside** the Suspense boundary (tabs stay visible while content loads), and the boundary lives **inside** PanelSwitcher and must stay mounted across switches — per-panel `<Suspense>` wrappers would flash their fallback on every switch.
**Gotchas.** _None._
**Example.** BatchSchedule builds one panel per phase from a `.map()` — the array-child case above.

## Action + modal screens (`component/action/`, `screen/*-modal/`)

**Purpose.** One component for "a button that opens a modal" — the tab-row actions and the list rows' delete affordance both go through it.
**Where.** `component/action/`; its content lives in a top-level modal screen — `screen/batch-create-modal/`, `recipe-create-modal/`, `recipe-edit-modal/`, `batch-delete-modal/`, `recipe-delete-modal/`. Each default-exports a component, takes ids as props, owns its own action, and renders a `ModalScreen`. `Action` owns the dialog ref and the Suspense boundary, so the content is plain config with no close handle.
**Invariants.**
- ⚠️ **`className` REPLACES the default `"btn-sm text-primary"`, it does not append to it.** A caller wanting `btn-xs` cannot simply add it beside `btn-sm`: daisyui size classes collide and **CSS order decides the winner, not the order they appear in the attribute**. Swapping the variable half is what makes the delete button's `btn-xs text-error absolute …` work at all.
- ⚠️ **`label` is the accessible name**, rendered as visible text unless `iconOnly`. Same convention as design's `DataGridAddButton`/`DataGridRemoveButton`, for the same reason — a glyph has no text to fall back on. The list rows' delete button is named `Delete <name>`, which two specs locate it by.
**Gotchas.** ⚠️ **`modalContent` is mounted eagerly** — `Modal` renders its children unconditionally, closed until toggled (see `packages/e2e/CLAUDE.md`, which relies on the dialog always being in the DOM). So a modal screen used **per row** must not do a suspenseful read: it would fire one query per row. `BatchCreateModal` reads its recipe via `useRecipeResource` and is fine because it is one per screen; `BatchDeleteModal`/`RecipeDeleteModal` take `name` as a prop instead. A create modal is one per screen; a delete modal is one per row.
**Example.** `<Action label={`Delete ${batch.name}`} icon={Trash} iconOnly className="btn-xs text-error absolute top-1.5 right-1.5" modalContent={<BatchDeleteModal batchId={batch.id} name={batch.name} />} />`

## Styling (Tailwind v4 + DaisyUI v5, nord theme)
**Purpose.** CSS-first config, no tailwind.config file, no PostCSS. **design owns the shared tokens** — the daisyui `nord` theme declaration, `--font-sans`, and the SRM `--color-beer-1`…`--color-beer-50` scale (rendered by design's `SrmAvatar`) live in `packages/design/src/tokens.css`; app and www each `@import "@brewdocs.beer/design/src/tokens.css";` it by bare specifier rather than declaring their own copies. Remaining app-only tokens (`--breakpoint-xs`, `--text-2xs`, the `--radius-selector` override, `--leading-11/12`, `.dg-collapsed ~ *`) stay in `packages/app/src/styles.css` — only what's byte-identical across consumers has moved so far.
**Where.** `src/styles.css` — the `@import` of design's `tokens.css`, the app-only `@theme` block, the `@source` for design, and unlayered `:root` overrides at the bottom. `packages/www/src/styles/global.css` is the minimal counterpart (just the `tokens.css` import + `@source`).
**Invariants.**
- ⚠️ `@source` and `@import` are unrelated mechanisms and **both are required** — don't conflate them. `@source "../../design/src";` makes Tailwind's *class scanner* look inside design's `.tsx` files for utility classes it should generate; `@import "@brewdocs.beer/design/src/tokens.css";` ships design's *token declarations* (the `@plugin`/`@theme` text) into the consumer's own Tailwind pipeline. Removing either silently drops styling with no build error — verify visually, not just by a green build.
- ⚠️ The bare-specifier import resolves via normal Node resolution (follows the workspace symlink) — this is *different* from Tailwind's directory auto-scan, which doesn't follow symlinks (that's why `@source` must be spelled out explicitly).
- ⚠️ `tokens.css` must never `@import "tailwindcss"` — every consumer (and `design.css` itself) already does, and a double import breaks the build.
- ⚠️ DaisyUI theme variables live in the `base` cascade layer, which beats `@theme` (the `theme` layer) — overriding a daisyui token (e.g. `--radius-selector`) requires a plain **unlayered** `:root {}` rule.
- ⚠️ Some DaisyUI behaviors are compound selectors keyed to **literal class names** (e.g. `.collapse`'s arrow needs the literal `collapse-arrow`) — applying them only via responsive variants (`max-lg:collapse-arrow`) silently breaks them.
- ⚠️ Don't add a `tabIndex` to a `.collapse` element — it force-opens via `:focus-within` in v5.
**Gotchas.** Tailwind utilities override DaisyUI component styles (cascade layers), so `checked:bg-primary` etc. on components is the intended customization mechanism.
- ⚠️ `.no-scrollbar` (unlayered, bottom of `styles.css`) hides a scrollbar without hiding the overflow — Tailwind ships no utility for it. It exists for the **compact** PanelSwitcher tab bar, which is a single scrolling row: a visible horizontal scrollbar inside a 40px bar costs more than it explains. ⚠️ DaisyUI's `.tabs` is `flex-wrap: wrap`, so that bar *wrapped* rather than overflowing until `flex-nowrap` was added — measured at 390px, it went to two rows and 72px at five phases. The scroll only works with all three together (`flex-nowrap` + `overflow-x-auto` + `.no-scrollbar`), and PanelSwitcher's effect centring the active tab is what keeps a scrolled-away tab reachable. ⚠️ `scroll-px-1` is load-bearing too: `.tabs-box` carries `padding: .25rem`, so the first tab's snap edge sits 4px inside a snapport that starts at 0 — without matching scroll-padding, snapping drags the bar back to `scrollLeft: 4` every time it reaches the left edge, even with the selected tab already in view.
**Example.** The unlayered `--radius-selector` override at the bottom of `styles.css`. `packages/www/src/styles/global.css` is the minimal working example of the shared-tokens stack; `packages/app/src/styles.css` is the maximal one (adds its own app-only tokens on top).

## kb serving during dev/build
**Purpose.** Serve kb data from a symlink in dev, and deliberately keep kb **out** of the app's build output.
**Where.** `npm run build-kb` (`npm --prefix ../kb run build`) then `npm run link-kb` (symlinks `public/kb → ../../kb/dist`), both wired to `predev` only.
**How it works.** `predev` is `build-kb && link-kb`, and both run **only via `predev`** (dev). The pre-`build` hook is named `devprebuild`, *not* `prebuild`, on purpose — so neither fires before `vite build`, keeping the kb symlink/JSON out of `dist` and the app S3 bucket. kb ships independently to its own bucket (`app-kb-prod`, served at `/kb/*`), so the app must not carry its own copy. ⚠️ `build-kb` uses `npm --prefix ../kb` rather than `npm run build -w packages/kb` — kb's builder resolves `data/`/`dist/` off `process.cwd()`, and `-w` doesn't resolve from inside a workspace package (only from the repo root).
**Invariants.** ⚠️ **Don't "fix" `devprebuild` to `prebuild`** — that reintroduces kb into the app publish.
**Gotchas.**
- ⚠️ **The symlink alone is not enough — kb must be *built* first.** kb's own `build` runs on `postinstall` only, so `git pull && npm run dev` used to point the symlink at a `dist/` predating any newly-added resource. Vite's SPA fallback then answers the missing `/kb/<resource>.json` with **`index.html` and a `200`**, so the failure surfaces as a JSON parse error inside `importResource` — a *"Failed to load static resource"* far from its cause, pointing at the network where nothing is wrong (seen live as #367: `Recipes → My Recipes` dying on a missing `recipe-templates.json`). Two guards: `predev` now builds kb before linking it, and `importResource` names the stale-`dist` cause when a response isn't a `{version, data}` envelope.
- A clean/CI build (no `public/kb`) produces `dist` with **no `dist/kb`** — so in prod the SW does *not* precache kb; offline kb comes entirely from the IndexedDB hydration flow (_Offline-first kb data flow_). But once you've run the dev server, the leftover `public/kb` symlink makes a **local** `npm run build` include + precache `dist/kb/*.json` — so a local `build`/`preview` misrepresents prod offline behavior (`rm public/kb` to reproduce CI).
**Example.** _None._

## Linting
**Purpose.** eslint 9 flat config, the verification gate (`npm test` = `eslint .`). **Ratchet policy: errors block, warnings inform** — `npm test` exits 0 while warnings remain.
**Where.** Shared base: `packages/core/eslint.config.base.js` (dev tooling, **not** `core/src`). Per-package overlays: `packages/app/eslint.config.js`, `packages/www/eslint.config.js`, `packages/design/eslint.config.js`.
**How it works.** The **base** (shared by app + www + design) holds the common rules: `@stylistic` (double quotes, semicolons, 4-space indent); `import-x/order` (external → `@brewdocs.beer/*` → `@/` → relative, alphabetized) + `import-x/no-relative-packages`; `react-hooks`; `no-restricted-imports` banning `lodash` and `../` parent-relative imports (use `@/`, which app and www alias to `src/*`; design has no `@/` alias — relative imports only). The import bans are **scoped to `src/**`** — root build/config files (`vite.config.ts`, `astro.config.mjs`) legitimately use relative cross-package paths. Overlays add only package-specifics: **app** → `react-refresh`, the `utils/func.ts` `any`-escape, the `routeTree.gen.ts` ignore; **www** → ignore the generated `.astro/` dir, allow triple-slash refs in `.d.ts`; **design** → no overlay rules (`.storybook/*` sits outside `src/`, so the `../`-ban doesn't reach its relative `design.css` import). www lints its `.ts`/`.tsx` (React islands + data); `.astro` files aren't linted (would need `eslint-plugin-astro`).
**Invariants.** ⚠️ Only `react-refresh/only-export-components` warnings are left standing (on purpose). New **errors** must be fixed or explicitly ruled.
**Gotchas.** ⚠️ The repo root hoists eslint **8.57.1** (eslintrc-era, chokes on flat config); each package resolves its own nested **9.x**. Run lint via `-w` or from inside the package (`npm run lint -w packages/app`), never the root binary.
**Example.** _None._
