# packages/design

Package-specific guidance. See the repo-root `CLAUDE.md` for universal rules (commands, dependency graph, the _Legend_ of field labels, contributing). Italic cross-references name a section that may live in another package's `CLAUDE.md` — most app subsystems are in `packages/app/CLAUDE.md`.

**Purpose.** React UI primitives that emit Tailwind/DaisyUI class strings, previewed and published as a static Storybook site. App and www still compile the class strings for their own bundles — design's own tailwind/daisyui deps exist only to render Storybook.
**Where.** `src/index.ts` (re-exports), `src/components/*` (co-located `*.stories.tsx`), `src/tokens.css` (the consumer-importable shared token fragment — daisyui `nord` + `--font-sans`; no `@import "tailwindcss"`, since consumers already have one), `src/design.css` (the Storybook entry — `@import "tailwindcss"` + `@import "./tokens.css"`), `.storybook/` (`main.ts` + `preview.tsx`; `manager.ts` + `theme.ts` brand the manager shell from tokens — see _Gotchas_), `tsconfig.json`, `eslint.config.js`. See [`DESIGN.md`](DESIGN.md) for the long-form design system doc (color, typography, spacing, radii, components).
**Surface.** One bullet per component or family. ⚠️ Keep it that way — this was a single
paragraph and collided in **four** consecutive epic merges, because every design-touching
branch appends to the same line. A new primitive gets its **own bullet**; appending to an
existing one re-creates the conflict.

- **Typography** — `ScreenH1–H5`/`ScreenP`.
- `ErrorMessage` — migrated from app's `Error`, renamed on the move since `Error` shadows the JS global.
- `Hero`.
- `Screen`/`ScreenTwoCol` — layout containers, single- and two-column page wrappers, migrated from app's `component/screen`. ⚠️ Distinct from the `Screen*` typography scale despite the shared name prefix.
- `InputText`, `InputDate`, `InputSelect` — ⚠️ `InputText` blurs on Enter when an `onBlur` handler is present; that's how "press Enter to commit" works app-wide.
- `Textarea` — multi-line free-text input. Mirrors `InputText`'s `value`/`onChange`/`onBlur`-to-commit shape but drops `align` and the Enter-to-blur `onKeyDown`, since a `<textarea>` needs Enter to insert a newline; commit is blur-only.
- `SearchBar` — a thin `InputText` wrapper, and the first design component to import another via `@/`.
- `Modal`/`ModalTitle`/`ModalFooter`/`ModalScreen`/`useModal` — the `<dialog>`-backed modal family. `useModal` returns a ref + toggle handler; `ModalScreen` composes `ModalTitle`+`ModalFooter` as the standard body scaffold.
- `Popover` — a lightweight anchored info bubble: hover-to-open on desktop, tap-to-open on mobile, dismissed by outside click/blur/`Escape`. A plain `relative`/`absolute` React component rather than `<dialog>` or DaisyUI's native `popover` attribute, since neither gives hover-to-open, and it does no viewport-edge flipping. `closeDelayMs` (default `0`, i.e. unchanged) defers only the **`onMouseLeave`** close, so a *moving* trigger can slide out from under a stationary cursor without dismissing itself mid-read; every other close path — click, `Escape`, blur, outside pointerdown — is immediate and cancels a pending close, as does re-entering.
- **svg icons** — `Hamburger`, `Plus`, `Pencil`, `Chevron`, `Cancel`, `Trash`, `UpDown`, `Minus`, `LockClosed`, `Play`, `Pause`.
- **DataGrid family** — `DataGrid`/`DataGridRow`/`DataGridHeaderRow`/`DataGridSubheaderRow`/`DataGridLabel`/`DataGridLabelNote`/`DataGridInput`/`DataGridSelect`/`DataGridCheckbox`/`DataGridAddButton`/`DataGridAddRow`/`DataGridRemoveButton`. The dense editable-grid family used by batch planning and recipe editing — migrated from app's `component/data-grid`, default exports converted to named; app's 13 files are now re-export shims. The two icon-only buttons take `label` (their accessible name), `title` and `disabled`, so a caller can render a control disabled with the reason in `title` — app's Phases panel does this once a batch has progressed.
- `SrmAvatar`/`SrmTag` — the SRM beer-colour swatches. `SrmAvatar` migrated from app's `component/srm-avatar` together with the `--color-beer-*` tokens it renders (see _Styling_; app's file is now a re-export shim); `SrmTag` is the same colour sized for a single dense grid row — a `size-3.5` `aria-hidden` inline dot, so its SRM value must be rendered as text alongside it, taking only the `bg` class from the triple plus a hairline border for legibility. ⚠️ Both bucket through the one exported `findSrmClasses` in `srm-avatar/constants.tsx` — a new SRM-coloured primitive imports that rather than re-walking `SRM_TO_HEX`, and `SrmTag` normalizes a non-finite `srm` to the lowest breakpoint before calling it (unguarded, `NaN <= key` is always false, so it would fall through to the SRM 40 fallback and render a stout brown for a missing value).
- `Timeline` — the hand-rolled inline-SVG elapsed-time line for the brew timer: a fluid-width `<svg>` with square `<rect>` markers at proportional offsets; x-axis only, no y-axis data, no chart library. It stays dumb — `onMarkerHover`/`onMarkerClick` hand back the marker plus its `percent` along the line, and any `Popover` overlay is the consumer's to position, since a `Popover` renders a `<div>` and so cannot be nested inside the `<svg>`. ⚠️ A running timer re-scales the line every tick, so `markerTransitionMs` transitions the marker `<rect>`'s **`x` geometry property** — CSS-animatable SVG geometry, not a `transform`, since the `x` is a percentage of the fluid width and a `transform` translate takes user units. Set it to the consumer's tick interval; leave it unset and markers jump.
- `BrewTimer` — the brew-day timer shell composed from `Timeline` + `Popover` + the `Modal` family: play/pause, an `HH:MM:SS` up-counter, marker popovers and a quick-milestone prompt. Fully controlled and stub-driven — it owns no timer state, no ticking and no persistence, and takes its reading-kind picker as plain `InputSelectOption[]` props. ⚠️ **The user-facing word is "Reading"; the model behind it is a `Milestone`, and that split is deliberate** — every string a user reads or hears says "Reading" (`aria-label="Log reading"`, the "Quick reading" modal, its "Reading kind"/"Reading measurement"/"Reading value" controls), while the type, the props (`milestoneKindOptions`, `onQuickMilestone`), the filename and app's `{on:"milestone"}` tracker ref all keep `milestone`. ⚠️ It does **not** ask which phase — the consumer resolves the current phase and passes `phaseLabel` for display, so the brewer isn't answering a question the app can already answer. `parameterOptions` is a `Record<kind, InputSelectOption[]>`: a kind listed there gets a second dropdown before the value, which is how water's seven measurements are chosen without the component knowing what water is. Marker popovers are hit targets laid *over* the `Timeline`'s `<svg>`, not inside it, so it recomputes each marker's percent; ⚠️ a marker's **visual** size and its **hit target** are deliberately separate and must stay that way — `markerSize` (10) sizes only the `<rect>` `Timeline` draws, while `BrewTimerMarkerOverlay`'s transparent `<button>` is `max(markerSize, 24)` centred on the same point, because WCAG 2.2 *Target Size (Minimum)* wants 24×24 CSS px and a 10px box is close to unhoverable on a *moving* marker. Collapsing them back into one number re-breaks it. Oversized targets on an elapsed-relative line necessarily overlap (markers compress toward 0 as `elapsedSeconds` grows), so the overlay makes the winner deterministic instead of DOM-order-by-accident: `place()` sorts ascending by `offsetSeconds` and z-indexes in that order — **the later marker is on top** — and it owns a single `openMarkerId`, passing `open`/`onOpenChange` so only one popover exists at a time and the open marker is raised above every hit box (each z-indexed wrapper is its own stacking context, so the popover's `z-50` is otherwise scoped to its own marker and gets buried by the next one). It passes `closeDelayMs={150}`; the Global/Phase scope toggle is visual only, with Phase disabled until phases are automated. ⚠️ The control bar is two stacked groups below `sm` — play+counter, then scope toggle + Milestone spread edge-to-edge — because at phone widths the single row overflowed; keep any new control inside the second group rather than adding to the first. Every control also steps down a size below `sm` (`btn-xs sm:btn-sm`, counter `text-lg sm:text-2xl`, card `p-2 sm:p-3`), so a new button wants the responsive size pair, not a bare `btn-sm`.
**Invariants.** ⚠️ Class strings must be valid **DaisyUI v5 / Tailwind v4** — app and www are what compile them for the real app (via `@source "../../design/src"` + `@plugin "daisyui"`); Storybook compiles them too now, but only for its own preview. design now has a `@/*` → `./src/*` alias like app (`tsconfig.json`) — cross-component imports must go through it, since the shared eslint base bans `../` inside `src/**` (see _Linting_). ⚠️ design declares no `tailwindcss`/`daisyui` runtime dependency for consumers — `tokens.css`'s `@plugin`/`@theme` resolve against **the consumer's own** Tailwind pipeline (see _Styling_); adding those as design deps risks a second hoisted copy drifting from app/www's.
**Gotchas.** `.storybook/main.ts` wires the Tailwind v4 Vite plugin in explicitly via `viteFinal` — Storybook's bundled Vite instance doesn't auto-discover a project `vite.config.ts` (design has none), so without it `design.css`'s `@import`/`@plugin`/`@theme` directives would ship uncompiled. The same `viteFinal` also carries the `@/` alias's `resolve.alias` entry (mirroring `app/vite.config.ts`) — `tsconfig.json`'s `paths` only satisfies the type-checker, not Storybook's bundler. ⚠️ `main.ts` also **brands the manager (shell) from our tokens**: at config-load (Node) it reads `src/tokens.css` + daisyui's `nord` theme CSS, flattens the nord **oklch** palette to hex with `culori` (devDep — Storybook's `polished` opacifies several theme vars and throws on oklch), and writes `.storybook/tokens.generated.ts` (git-committed but **eslint-ignored**, like a `*.gen.ts`; regenerated deterministically each start). `theme.ts` builds the `create()` theme from that map — nord throughout, including the two `polished`-run accents (`colorPrimary`/`colorSecondary` = nord's Frost blue, matching the blue that dominates app/www) — and `manager.ts` applies it via `addons.setConfig`. ⚠️ Generation runs in Node because the **manager builder can't `import … ?raw`** (a Vite-only feature that works in the preview but not the shell); reading the CSS in the manager bundle instead throws at init and silently reverts to the default theme. `input-checkbox` and `input-unit` (dead, non-compiling stubs, never exported) were deleted — reintroducing either needs a real implementation, not the old stub.
**Example.** _None._
